# Part 2 — Addendum
GM One Stop Service • 3 October 2026 • Asia/Bangkok

เพิ่มเฉพาะ 4 เรื่องตามคำสั่งล่าสุด มีลำดับเหนือ Part 2 และ C1–C11 เฉพาะจุดที่เปลี่ยน ส่วนอื่นคงเดิม Addendum นี้รวมในเกณฑ์เปิดด่าน A; ผลต่อ SLA และกราฟเต็มเปิดในด่าน B

## A1. ช่องทางแจ้งเตือนสำรอง — ด่าน A

### A1.1 การแจ้งในเว็บ
- หน้าแรกมีแถบ “มี X งานรอคุณยืนยัน” นับงานที่ requester_id เป็นผู้ใช้ปัจจุบัน, status = completed และยังไม่มี closed_at เมื่อกดเปิดคำขอของฉันที่กรองรอยืนยันไว้แล้ว
- แสดงเมื่อ X > 0 เท่านั้น ตัวเลขต้องมาจากสิทธิ์ผู้ใช้ปัจจุบัน ไม่ใช้จำนวนทั้งบริษัท
- คำขอของฉันแสดงจุดพร้อมข้อความ “มีอัปเดตใหม่” ในงานที่มีเหตุการณ์ที่ผู้ใช้มีสิทธิ์เห็นเกิดหลังการเปิดรายละเอียดครั้งล่าสุด ใช้ทั้งแท็บที่ฉันขอและเกี่ยวข้องกับฉัน
- เปิดบอร์ด เห็นการ์ด เปิด Slack/email หรือการโหลดรายละเอียดล้มเหลว ไม่นับว่าเปิดอ่านรายละเอียดแล้ว การเปลี่ยนสถานะอ่านไม่กระทบ last_updated_at หรือ stale
- ถ้ามีเหตุการณ์เข้ามาระหว่างอ่าน ให้ถือว่าอ่านเฉพาะส่วนที่แสดงสำเร็จ ไม่ล้างจุดของเหตุการณ์ที่ยังไม่ได้แสดง
- ไม่สร้าง notification center, inbox การแจ้งเตือน หรือ web push เพิ่มใน Phase 1

### A1.2 เลือกช่องทางส่งรายผู้รับ

| เงื่อนไข | ช่องทาง |
|---|---|
| จับคู่ Slack user ได้ | ส่ง Slack ตามเหตุการณ์เดิม |
| จับคู่ Slack ไม่ได้ แต่มีบัญชี @tdfb.co ใช้งานได้ | ส่ง email แทน |
| ไม่มีบัญชีบริษัท/ไม่มีช่องทางที่ใช้ได้ | ไม่ส่งไปบัญชีที่เดาจากชื่อ ให้ GM ติดต่อเอง |
| ช่องทางที่เลือกส่งล้มเหลว | งานยังบันทึกได้ แสดงผลการส่งแก่ GM และให้ลองใหม่ตามกติกาเดิม |

- กติกานี้ใช้กับผู้ขอ ผู้รับแจ้งของช่วงรอ และ GM ผู้รับแจ้งตามเหตุการณ์ ไม่ส่งสองช่องทางซ้ำเป็นค่าเริ่มต้น
- การสลับจาก Slack ที่ล่มไป email อัตโนมัติไม่ได้เพิ่มในรอบนี้ คงรายงานข้อผิดพลาดและ retry; วิธีส่ง email และการป้องกันส่งซ้ำกำหนดใน Part 6
- Slack/email ใช้เลขงาน ลิงก์ และขอบเขตข้อความเดียวกัน งานลับใช้ข้อความกลาง ไม่ใส่ชื่อ รายละเอียด หมายเหตุ รูป หรือไฟล์ใน subject/body
- ลิงก์ต้อง login และตรวจสิทธิ์ล่าสุด ไม่มีลิงก์ที่ให้สิทธิ์ด้วยตัวมันเอง และไม่มีปุ่มใน email ที่เปลี่ยนสถานะทันที
- “ส่งแล้ว” หมายถึงผลการส่งที่ระบบตรวจได้ ไม่ใช่หลักฐานว่าผู้ใช้เปิดอ่าน
- เมื่อผู้ขอไม่มีช่องทางใช้ได้ หรือการแจ้งที่จำเป็นยังส่งไม่สำเร็จ ให้ GM เห็นป้าย “ผู้ขอยังไม่ได้รับแจ้ง” พร้อมสาเหตุ ป้ายและข้อมูลช่องทางไม่อยู่บนบอร์ดสรุปทั่วไป
- ป้ายนี้ไม่ใช้กับ gm_task ซึ่งไม่มีผู้ขอ และไม่ถูกล้างเพียงเพราะ GM กดเสร็จ ผู้ขอเปิดรายละเอียดที่มีอัปเดตนั้นสำเร็จถือเป็นหลักฐานการรับรู้ในเว็บได้ การแจ้งด้วยตนเองใช้ประวัติการติดต่อจริง ไม่อนุมานจากข้อความอิสระหรือสถานะ completed

### A1.3 ไม่มีบัญชีบริษัท
- หน้า QR และ login มี “ไม่มีบัญชีบริษัท? แจ้งทีม GM” พร้อมช่องทางที่ใช้ได้จริงโดยไม่ต้อง login เช่น เบอร์ที่ Admin ระบุ
- เปิดเผยเฉพาะข้อมูลติดต่อที่ Admin กำหนดให้ใช้ในหน้านี้ ไม่เปิดบอร์ด รายชื่อพนักงาน หรือรายละเอียดคำขอก่อน login
- GM ใช้ F03 เปิดแทนแบบชื่อข้อความ: origin = gm_on_behalf, created_by_id = GM, ไม่มี requester_id
- ไม่มีขั้นยืนยันจากผู้ขอ งานปิดเมื่อ GM กดเสร็จตาม C2; ไม่เพิ่ม anonymous submission หรือการ login ด้วยบัญชีส่วนตัว

## A2. ฝ่ายที่รอตอบ “ฝั่งฉันเรียบร้อยแล้ว” — ปุ่ม A / ผล SLA B

### A2.1 สิทธิ์และผลของปุ่ม
- ผู้รับแจ้งที่ยืนยันไว้สำหรับช่วงรอปัจจุบัน และยังมีสิทธิ์รายละเอียด เห็นปุ่มในหน้ารายละเอียดเมื่อ status = waiting และช่วงนั้นยังไม่เคยตอบ
- ใช้เฉพาะ person และ team ที่มีผู้ติดต่อภายใน ไม่ให้สิทธิ์นี้จาก related_person_ids เพียงอย่างเดียว และไม่ให้ผู้รับของช่วงรอเก่ากดแทนช่วงใหม่
- กดเปิดแผงสั้น มีหมายเหตุไม่บังคับ จากนั้นยืนยัน ระบบบันทึก event = waiting_party_responded และ responded_at ใน history ของช่วงรอนั้น พร้อมผู้ทำรายการ
- แจ้ง GM ผู้รับผิดชอบผ่านช่องทางที่ใช้ได้ หากยังไม่มอบหมายให้แจ้งทีม GM ตามกติกางานไม่มอบหมาย
- การ์ดขึ้น “ฝ่ายที่รอตอบกลับแล้ว” พร้อมเวลา GM ยังเป็นผู้ย้ายกลับกำลังทำ
- ไม่เปลี่ยน status, waiting_on, waiting_since, last_updated_at หรือ stale จากการตอบนี้
- contractor / government / other ไม่มีปุ่มนี้ GM เปลี่ยนสถานะเมื่อได้รับคำตอบ

### A2.2 ความหมายของผู้ติดต่อหลายคน — assumption สำหรับ Phase 1
- ผู้ติดต่อของ team 1–3 คนเป็นตัวแทนฝ่ายเดียวกัน ใช้คำตอบแรกที่บันทึกสำเร็จเป็น responded_at ของช่วงรอนั้น ไม่ต้องรอครบทุกคน
- แผงยืนยันบอกว่า “การตอบนี้หมายถึงฝั่ง [ทีม] เรียบร้อยแล้ว” ผู้ติดต่อคนอื่นเห็นผลตอบเดิมและไม่สร้างผลตอบซ้ำ
- ถ้างานยังต้องรอเพิ่มเติม GM เปิดช่วงรอใหม่อย่างชัดเจนพร้อมข้อมูลที่รอเพิ่ม เก็บช่วงเดิมและ responded_at เดิมไว้ ไม่แก้เวลาตอบย้อนหลังเพื่อเริ่มพัก SLA ใหม่

### A2.3 เปลี่ยนนิยามเวลาโดยไม่เพิ่มสถานะ

| ตัววัด | ก่อนฝ่ายตอบ | หลัง responded_at ขณะที่ status ยังเป็น waiting |
|---|---|---|
| เวลารอฝ่ายนั้น | สะสมเวลาจริงต่อเนื่อง | หยุดที่ responded_at |
| SLA clock ของ GM ใน B | พัก หาก milestone ยังไม่จบ | กลับมาสะสมตาม unit/calendar ของ sla_snapshot |
| อายุงานรวม | เดินต่อเนื่อง | เดินต่อเนื่อง |
| stale | เดินตามวันทำการจาก last_updated_at | เดินต่อจากค่าเดิม |

ตัวอย่างวันทำการ: เข้ารอ 10:00 → ฝ่ายตอบ 12:00 → GM ย้ายกลับกำลังทำ 14:00 กราฟคิดเวลาของฝ่ายนั้น 2 ชั่วโมง ส่วน 12:00–14:00 เป็นเวลาของ GM ตามเกณฑ์ SLA ไม่คิดให้ฝ่ายที่ตอบแล้ว หากเป็นวันหยุด SLA แบบ business_days ยังสะสมเฉพาะวันเปิดทำการ แต่เวลารอจริงยังหยุดที่เวลาตอบ

- ถ้าไม่มีคำตอบจากปุ่ม ให้จบเวลารอเมื่อออกจาก waiting หรือเปลี่ยนฝ่ายตามกติกาเดิม
- SLA ที่ถึง milestone แล้วไม่ถูกเปิดเดินใหม่เพราะเหตุการณ์ตอบ; รอบเปิดกลับยังใช้กติกาเดิม
- ใน B ป้าย “พัก SLA” ใช้เฉพาะช่วงที่ยังรอคำตอบ ไม่ตัดสินจาก status = waiting อย่างเดียว
- ปุ่มต้องตรวจช่วงรอ สิทธิ์ และสถานะล่าสุด กดพร้อมกันหรือ retry ต้องเกิดผลครั้งเดียว
- เพิ่มตัวอย่างตอบก่อน GM ย้ายสถานะ ตอบวันหยุด สลับช่วงรอหลายรอบ และกดตอบซ้ำ ใน unit test ของ pure functions เวลาเดิมตาม C8; เป็นเกณฑ์สำหรับ build ยังไม่ได้ทดสอบ implementation ในเอกสารนี้
- ข้อกำหนดนี้แทนข้อความเดิมที่ให้พัก SLA ตลอดทุกเวลาที่เป็น waiting และแทนจุดจบเวลารอที่อิงการย้ายสถานะเพียงอย่างเดียว

## A3. ลาพร้อมวันสิ้นสุดและงานยังไม่มอบหมาย — ด่าน A

- presence_status = “ลา” เลือกวันสิ้นสุดได้ ใช้วันตาม Asia/Bangkok และรวมวันสิ้นสุดนั้น
- ถ้ามีวันสิ้นสุด ให้คง “ลา” ผ่านการรีเซ็ตสิ้นวันจนสิ้นวันดังกล่าว แล้วกลับ “ไม่ระบุ” เมื่อเข้าวันถัดไป
- ถ้าไม่ใส่วันสิ้นสุด ให้ใช้พฤติกรรมเดิม: รีเซ็ตเป็น “ไม่ระบุ” เมื่อสิ้นวันปัจจุบัน เป็นค่าเริ่มต้นเพื่อไม่ให้ลาค้างไม่มีกำหนด
- ไม่รับวันสิ้นสุดก่อนวันปัจจุบัน; เมื่อเปลี่ยนเป็น presence อื่นให้ล้าง leave_until_date ที่ผูกกับการลารอบเดิม
- GM เปลี่ยน presence เองก่อนกำหนดได้ งาน reset ต้องไม่ล้างค่าที่ตั้งใหม่ และไม่แก้ focus_request_id จากการเปลี่ยน presence
- ตอนบันทึกงานใหม่ ตรวจสถานะลาของผู้รับผิดชอบเริ่มต้นล่าสุด หากลาให้ status = queued, assignee_id ว่าง และแจ้ง GM ทั้งทีมแทนการมอบหมายอัตโนมัติ
- บอร์ดมี filter “ยังไม่มอบหมาย” ตั้งแต่ A การ์ดแสดงผู้รับผิดชอบเป็น “ยังไม่มอบหมาย” และ GM รับเรื่องได้จากการ์ด
- กติกานี้ใช้กับการมอบหมายเริ่มต้นอัตโนมัติ งานที่ GM ตั้งใจเลือกผู้รับผิดชอบเองเป็นการมอบหมายโดยคนและต้องแสดงสถานะลาให้เห็น
- ไม่ย้ายงานเก่าของผู้ลา และไม่มอบหมายงานค้างกลับให้เองเมื่อพ้นวันลา
- ไม่เพิ่มระบบอนุมัติลา ปฏิทินเวร หรือการเลือกคนสำรองอัตโนมัติ

## A4. เลขงานที่อ่านออกเสียงได้ — ด่าน A

- ทุกงานมี request_number เช่น GM-0427 แสดงบนการ์ด รายละเอียด Slack และ email ตั้งแต่ A และใช้ค้นใน B
- request_number เป็นเลขอ้างอิงที่คนใช้ร่วมกัน ไม่แทน request_id ภายในและไม่ใช้เลขงานเป็นหลักฐานสิทธิ์
- ลำดับต่อเนื่องชุดเดียว ไม่รีเซ็ตรายปี ไม่ใช้เลขเก่าซ้ำเมื่อยกเลิก และไม่ตัดเลขเมื่อเกิน 4 หลัก เช่น GM-10000
- แสดงเลขเมื่อยืนยันการบันทึกสำเร็จ ไม่แสดงเลขคาดเดาบนฟอร์ม; retry งานเดิมต้องได้งานและเลขเดิม
- งานลับยังมีเลขงาน แต่ไม่เผยเลขบนบอร์ดหรือหน้าแรกให้คนที่ไม่มีสิทธิ์ งานจาก Trello ใช้เลขเว็บควบคู่ป้าย “จาก Trello” เมื่อเปิด milestone นั้น
- วิธีออกเลขและรับมือการสร้างพร้อมกันกำหนดใน Part 6
