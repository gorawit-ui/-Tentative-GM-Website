# GM One Stop Service — Part 1: Product Requirements Document
Version 1.0 • 2 October 2026 • Timezone: Asia/Bangkok

เอกสารสำหรับออกแบบและส่งต่อ Claude Code โดยอ้างอิง brief และคำตอบ Part 0 ของเบนซ์ในวันที่ 2 ตุลาคม 2026 คำตอบล่าสุดมีลำดับเหนือสมมติฐานเดิม นี่คือข้อกำหนดผลิตภัณฑ์ ยังไม่ใช่ระบบที่สร้างหรือทดสอบแล้ว

Part นี้ครอบคลุมปัญหา เป้าหมาย ตัวชี้วัด ขอบเขต กติกาธุรกิจ และ user stories พร้อม acceptance criteria ส่วนแผนผังหน้าจอ UI tokens ต้นแบบ โครงสร้างฐานข้อมูล และ build plan จะอยู่ Parts 2–7 ตามลำดับ

## 1. ปัญหาและผลลัพธ์ที่ต้องการ

| รหัส | ปัญหา | ผลลัพธ์ที่ระบบต้องทำให้เกิด |
|---|---|---|
| P1 | งานกระจายหลายช่องทาง พนักงานต้องทักถามความคืบหน้า | เปิดคำขอและติดตามในเว็บเดียว เห็นคิวและผู้รับผิดชอบ |
| P2 | ข้อมูลไม่อัปเดตสม่ำเสมอ | อัปเดตงานง่าย เห็นงาน stale และติดตามต่อได้ |
| P3 | งานข้ามทีมไม่เห็นว่าติดอยู่ที่ใคร | ทุกช่วงรอมีฝ่ายที่รอ เวลาเริ่ม และเวลารอสะสม |
| P4 | GM&HR Scorecard ต้องกรอกมือทุกวันจันทร์ | คำนวณจากข้อมูลที่มีจริง พร้อมส่งออกและระบุข้อมูลที่ยังไม่เชื่อม |

**เป้าหมายหลัก:** KR2.2 — One Stop Service GM ที่พนักงานใช้เองได้ และทีม GM 3 คนดูแลต่อได้จริง

**ความเกี่ยวข้องกับ KR2.1:** มีลิงก์เข้าแอป expense tracking เดิมเท่านั้น ระบบนี้ไม่คำนวณหรืออ้างว่าทำให้การทดรองจ่ายลดจาก 3 วันเป็นครึ่งวันด้วยตัวเอง

**หลักการตัดสินใจ:** งานใหม่ที่มีผู้เกี่ยวข้องนอกทีม GM ต้องสร้างในเว็บ งานภายในล้วนใช้เว็บหรือ Trello ได้ เอกสารจริงยังเก็บใน Google Drive และ Request เป็นข้อมูลหลักของงานในเว็บ

## 2. ผู้ใช้และความรับผิดชอบ

| Role key | ชื่อบนหน้าจอ | สิทธิ์หลัก |
|---|---|---|
| requester | พนักงาน | เปิดและติดตามคำขอ ดูบอร์ดสรุป ดูรายละเอียดเฉพาะงานที่มีสิทธิ์ ยืนยันงานของตัวเอง |
| gm_staff | ทีม GM | รับเรื่อง มอบหมาย อัปเดตงาน จัดการคำขอ ดูบอร์ดและ Dashboard |
| gm_admin | ผู้ดูแลทีม GM | สิทธิ์ GM Staff และตั้งค่าประเภท SLA ปฏิทิน สถานที่ บริเวณ QR ผู้ใช้ และ mapping |
| viewer | ผู้ดูภาพรวม | ดูบอร์ดสรุปและทุกส่วนของ Dashboard ตามขอบเขตข้อมูลที่เปิดเผย ไม่มีสิทธิ์แก้งานหรือเปิดงานลับ |

สำหรับผู้ใช้บทบาท requester สิทธิ์เกี่ยวกับคำขอของตนเองและการเป็นสมาชิกทีมที่เกี่ยวข้องต้องตรวจจากความสัมพันธ์กับ Request จริง ส่วน viewer เป็นบทบาทดูบอร์ดสรุปและ Dashboard เท่านั้น ไม่รับสิทธิ์รายละเอียดหรือไฟล์แนบจากการเป็นสมาชิกทีม และไม่เห็นงานลับ นี่คือกติกาลำดับสิทธิ์ที่ใช้ใน Phase 1 เพื่อให้เงื่อนไข Viewer ชัดเจน

| บุคคล | ขอบเขตงานจาก brief |
|---|---|
| พี่ป๊อป Napat | Damage ขายมือสอง/Scrap อาคารสถานที่ บิลค้างรับ |
| เบนซ์ Gorawit | เอกสาร/สัญญา/ต่ออายุ ทะเบียนทรัพย์สิน ข่าวภาครัฐ BOI เพจปลอม GHPs |
| ป๊อป Sirirat | ซ่อม/maintenance จัดซื้ออุปกรณ์สำนักงาน รับของ Odoo คปอ. ลงทะเบียนเอกสาร/พัสดุ |

ประเภทแจ้งซ่อมตั้งผู้รับผิดชอบเริ่มต้นเป็น Sirirat โดย Admin แก้ได้ การมอบหมายต่อไม่จำกัดอยู่กับคนตั้งต้น งานอาคารสถานที่ที่ทับซ้อนกับงานซ่อมให้ GM ตัดสินใจและบันทึกการมอบหมาย ไม่สร้างคำขอซ้ำอัตโนมัติ

สถานที่แสดงชื่อตรงกันทุก Part: **WH300 / FAC16 / FAC17 / Office 195 / Cafe 222**

WH300 มีบริเวณ: ห้องแพ็คชั้น 1, ห้อง QA ชั้น 1, ออฟฟิศชั้น 2, คลังสินค้าชั้น 3, คลังสินค้าชั้น 4, ห้องเก็บของชั้น 5

บริเวณของอีก 4 สถานที่ในต้นแบบเป็น mock และต้องระบุว่าเป็นตัวอย่างก่อนนำไปใช้จริง

## 3. Success metrics ที่ผูกกับ KR2.2

ค่าด้านล่างเป็น **เป้าหมายเสนอสำหรับ pilot** ไม่ใช่ baseline หรือผลที่เกิดขึ้นแล้ว เก็บ baseline จากวิธีเดิม 1 สัปดาห์ก่อน pilot และประเมินหลังเปิดใช้ 30 วัน

| ตัวชี้วัด | นิยาม/วิธีวัด | เป้าหมายเสนอ | เชื่อมโยง |
|---|---|---|---|
| งานข้ามทีมเข้าระบบ | คำขอใหม่ที่เกี่ยวข้องนอก GM และมี Request ในเว็บ ÷ งานเข้าเกณฑ์ทั้งหมดจากการกระทบยอดช่องทางรับเรื่อง | 100% | P1, P3, KR2.2 |
| พนักงานเปิดเรื่องเอง | งานจากพนักงานที่ผู้สร้างเป็น requester ÷ งานจากพนักงานทั้งหมด รวมงานที่ GM ช่วยเปิดแทน | ≥ 80% | P1, KR2.2 |
| ความเร็วการแจ้งซ่อม | ค่ามัธยฐานจากเริ่มฟอร์มหลังเข้าสู่ระบบจนบันทึกสำเร็จ รวมการแนบรูป ในคำขอที่ส่งสำเร็จ | ≤ 90 วินาที และไม่เกิน 4 ขั้น | P1, KR2.2 |
| ค้นสถานะได้เอง | ผู้ทดสอบที่หาสถานะและผู้รับผิดชอบได้โดยไม่ต้องให้คนช่วย ภายใน 30 วินาที | ≥ 90% ในกลุ่มอย่างน้อย 10 คน ครบ 5 สถานที่ | P1, KR2.2 |
| ลดการทักถามสถานะ | จำนวนครั้งที่ถามสถานะต่อคำขอ 100 งาน เทียบ baseline ด้วยการจดนับแบบเดียวกัน | ลด ≥ 50% | P1, KR2.2 |
| สุขภาพข้อมูล | งานเว็บที่ stale ÷ งานเว็บสถานะรอคิว/กำลังทำ/รอผู้อื่น ณ เวลาเดียวกันทุกวันจันทร์ | ≤ 10% | P2, KR2.2 |
| ทำตาม SLA | งานที่ถึงเป้าหมายภายใน SLA ÷ งานที่ประเมินผลได้ ตามนิยามข้อ 6.7 | ≥ 90% | P2, P3, KR2.2 |
| งานรอมีข้อมูลครบ | งานรอผู้อื่นที่มี waiting_on และ waiting_since ÷ งานรอผู้อื่นทั้งหมด | 100% | P3, KR2.2 |
| ลดงานกรอก Scorecard ซ่อม | GM ได้ตัวเลขและ CSV งานซ่อมค้างโดยไม่ต้องนับทีละการ์ด | 0 ครั้งที่ต้องนับมือเพื่อสร้างตัวเลขซ่อมค้าง | P4, KR2.2 |

เป้าหมาย Scorecard ที่ผู้ใช้กำหนดแล้ว: **งานซ่อมค้าง ≤ 2 / เอกสารลงทะเบียนเกิน 3 วัน = 0 / ทรัพย์สินไม่ลงทะเบียน = 0 / สัญญารอดำเนินการ = 0**

การวัด adoption และการทักถามใช้การกระทบยอดโดย GM สัปดาห์ละครั้งร่วมกับข้อมูลในเว็บ ไม่เพิ่มระบบสำรวจหรือระบบอ่าน Slack ทั้งบริษัทใน Phase 1 หาก baseline เป็น 0 หรือจำนวนตัวอย่างน้อย ให้แสดงจำนวนจริงและระบุว่ายังเทียบเปอร์เซ็นต์ไม่ได้

## 4. ขอบเขตตาม Phase และการเปิดใช้

| ช่วง | สิ่งที่ต้องส่งมอบ | เกณฑ์ขอบเขต |
|---|---|---|
| เปิดใช้ระบบแจ้งซ่อมใน Q4 2026 | เข้าสู่ระบบ/สิทธิ์, หน้าแรก, แจ้งซ่อมและ QR, คำขอของฉัน/รายละเอียด, ทีม GM/FAQ, บอร์ด, Dashboard พื้นฐาน, Admin, ปฏิทิน/SLA/stale, ยืนยันและปิดอัตโนมัติ, audit history, CSV | ต้องทำวงจรแจ้งซ่อมครบทั้ง 5 สถานที่ รวมสิทธิ์ข้อมูลและกรณีผิดพลาด |
| ส่วนที่ต้องครบใน Phase 1 | แบบรับคำขอเอกสาร/ส่งเอกสารอย่างง่าย, ค้นหางาน, ประกาศ, ทัศนวิสัยงานภายใน, Dashboard ตาม brief, Slack actions/notifications/digest, PWA, ลิงก์ expense และ Sheets | แบบเอกสารสร้างและติดตาม Request ยังไม่เป็นทะเบียนเอกสาร |
| Milestone ท้าย Phase 1 | Trello → เว็บ แบบ read-only และกล่องรายการผิดกติกา | ห้ามเป็นเงื่อนไขขวางการเปิดแจ้งซ่อม หากไม่ทันเลื่อนไป Phase 2 ได้ |
| Phase 2 — Q1 2027 | ทะเบียนทรัพย์สิน/ผู้ครอบครอง/สถานที่/ประวัติซ่อม, ทะเบียนเอกสารและค้นหา/ขอเอกสาร, งานต่ออายุและสัญญา, Scorecard อีก 3 ตัว | ใช้ข้อมูลที่ย้ายและตรวจสอบจากทะเบียนจริง และระบุรายการตั้งต้นที่ใช้ตรวจ “ไม่ลงทะเบียน” |
| ไม่รวมใน Phase 1 | ระบบทดรองจ่ายใหม่, เชื่อม Odoo เพื่อทำธุรกรรม, Trello สองทาง, บัญชีผู้รับเหมาภายนอก, AI ทำนายซ่อม, ระบบอนุมัติจัดซื้อ, full offline write, dark mode UI | งานเหล่านี้ยังใช้ Request ติดตามได้เมื่อจำเป็น แต่ไม่สร้างระบบย่อยเพิ่ม |

**ข้อแลกเปลี่ยน:** เปิด maintenance ก่อนช่วยให้เริ่มใช้งานได้โดยไม่รอ Trello แต่ช่วงแรกยังต้องติดตามงานภายในบางส่วนที่ Trello; Slack ยังคงเป็นงานที่ต้องส่งใน Phase 1 และการเปิด pilot ของแกนหลักไม่เท่ากับประกาศว่า Phase 1 เสร็จครบแล้ว

## 5. คำศัพท์กลางและสิทธิ์ข้อมูล

### 5.1 งานเดียวกันทุกหน้าจอ

ใช้ Request เป็นงานหลักหนึ่งรายการ ไม่สร้างงานใหม่เมื่อย้ายสถานะ มอบหมาย หรือเปิดกลับ

| Field/แนวคิด | ความหมายที่ใช้ต่อทุก Part |
|---|---|
| type | ชนิดกระบวนการ เช่น maintenance, document_request, document_intake, internal_task |
| category | หมวดงาน GM หนึ่งใน 7 หมวด ไม่ใช่สถานะ และไม่ใช้แทน type |
| source | web หรือ trello; งานจาก Trello แสดงแบบ read-only |
| requester_id | ผู้ขอจริง อาจไม่มีในงานภายใน; GM ที่ช่วยเปิดแทนต้องบันทึกแยกจากผู้ขอ |
| assignee_id | ผู้รับผิดชอบหลักหนึ่งคน เพิ่มผู้เกี่ยวข้องผ่านทีมที่เกี่ยวข้อง |
| related_team_ids | ทีมที่เกี่ยวข้องและมีสิทธิ์ดูรายละเอียดตามนโยบาย |
| is_confidential | งานลับที่ต้องไม่แสดงรายละเอียดบนบอร์ดสรุป |
| waiting_on / waiting_since | ผู้ที่กำลังรอและเวลาเริ่มช่วงรอนี้ |
| last_updated_at | เวลาความคืบหน้าที่มีความหมายจาก GM; ใช้ตัดสิน stale |
| created_at | เวลาเปิดคำขอ ใช้เริ่มอายุงานรวม |
| completed_at | เวลา GM แจ้งว่าเสร็จในรอบล่าสุด |
| closed_at | เวลายืนยันหรือปิดอัตโนมัติในรอบล่าสุด; งานภายในไม่มี requester ปิดเมื่อ GM กดเสร็จ |
| history | ประวัติเหตุการณ์ ผู้ทำ เวลา และค่าที่เปลี่ยน เก็บรอบเก่าทั้งหมด |

หมวด GM ทั้ง 7: บริหารสินค้า Damage / เอกสารและธุรการ / ทรัพย์สินและอาคารสถานที่ / จัดซื้อทั่วไปและบิล / ภาครัฐ กฎหมาย Compliance / Project ปรับปรุงระบบ / กิจกรรมพนักงาน

งาน internal_task ใช้ติดตามหมวดเหล่านี้ได้ใน Phase 1 โดยไม่สร้างโมดูลเฉพาะเพิ่ม การเปิดฟอร์มเฉพาะของแต่ละหมวดไม่ใช่ขอบเขต Phase 1

| Status key | ชื่อบนหน้าจอ | ความหมาย |
|---|---|---|
| queued | รอคิว | รับเข้าระบบแล้ว ยังไม่เริ่มดำเนินการ |
| in_progress | กำลังทำ | GM รับและกำลังดำเนินการ |
| waiting | รอผู้อื่น | มีฝ่ายที่รอชัดเจน และหยุด SLA clock ของ GM |
| completed | เสร็จ | GM ทำเสร็จแล้ว อาจกำลังรอ requester ยืนยัน |
| cancelled | ยกเลิก | หยุดคำขอพร้อมเหตุผล |

- ชื่องานสรุปใช้ข้อความที่เปิดเผยได้ เช่น “แอร์ไม่เย็น — ห้องแพ็คชั้น 1” รายละเอียดส่วนบุคคล เบอร์โทร เลขเอกสาร และข้อความลับอยู่ในส่วนที่จำกัดสิทธิ์
- งานลับแสดงเพียง “งานภายใน X รายการ” สำหรับผู้ไม่มีสิทธิ์ ไม่มีรายการ ชื่อ ผู้ขอ ผู้รับผิดชอบ ประเภท หรือสถานที่ให้ไล่ย้อนหา
- Viewer เปิดทุก widget ได้ แต่ตัวเลขแยกสถานะ/คน/สถานที่/ฝ่ายที่รอและ CSV แถวรายงานทั่วไปไม่นำรายละเอียดงานลับมาปะปน งานลับมีเพียงจำนวนรวมแยกต่างหาก ไม่แจกแจงตาม filter คน ประเภท หรือสถานที่
- GM เห็นข้อมูลรวมที่มีงานลับได้ตามสิทธิ์ จึงต้องแสดงขอบเขตชุดข้อมูลที่ใช้คำนวณกำกับเสมอ
- ผลค้นหา การแจ้งเตือน ลิงก์ตรง การส่งออก และข้อมูลที่ส่งถึงเครื่องผู้ใช้ต้องเคารพสิทธิ์เดียวกัน ห้ามส่งข้อมูลครบแล้วซ่อนเฉพาะหน้าจอ
- สมาชิกทีมที่เกี่ยวข้องมาจากข้อมูลสมาชิกที่ Admin จัดการได้ ไม่ใช่การพิมพ์ชื่อทีมเองเพื่อรับสิทธิ์
- สิทธิ์ลิงก์ Google Drive ยังคงขึ้นกับ Drive ด้วย เว็บไม่ให้สิทธิ์ไฟล์ต้นทางอัตโนมัติ
- งานที่เกี่ยวกับสัญญา เอกสารบริษัท และเรื่องบุคคลตั้งธงลับเริ่มต้นในแบบรับเรื่อง; GM ตรวจได้ และ GM Admin เท่านั้นที่ปลดธงพร้อมเหตุผล เป็นค่าเริ่มต้นการออกแบบที่ระบุไว้เพื่อป้องกันการเปิดเผยโดยผิดพลาด

## 6. กติกาธุรกิจที่ต้องใช้ร่วมกัน

### 6.1 ปฏิทินและการนับวัน

ข้อที่ผู้ใช้ยืนยัน:
- ลงทะเบียนเอกสาร 3 วัน, stale 3 วัน และ SLA ทั่วไป ใช้วันทำการเป็นค่าเริ่มต้น
- Admin ตั้งวันทำการ/วันหยุดของบริษัทและแยก override ตามสถานที่ได้
- SLA แต่ละประเภทเลือก business_days หรือ continuous_24h ได้
- ไฟดับ/อินเทอร์เน็ตล่มวัดการประสานช่างภายใน 1 วันทำการ

รายละเอียดเพิ่มเพื่อให้ coding agent ไม่ต้องเดา:
1. Phase 1 ตั้งเฉพาะวันเปิดทำการและวันหยุด ยังไม่มีตารางกะหรือเวลาเปิด–ปิดรายชั่วโมง
2. 1 วันทำการหมายถึงเวลาสะสม 24 ชั่วโมงที่อยู่บนวันที่เปิดทำการตามปฏิทินของสถานที่นั้น วันหยุดมีน้ำหนัก 0 นี่เป็นข้อกำหนดเพิ่มที่ยังปรับได้ก่อน build
3. ตัวอย่างปฏิทินจันทร์–ศุกร์ ไม่มีวันหยุด: เริ่มศุกร์ 2 ต.ค. 2026 เวลา 16:00 เป้าหมาย 1 วันทำการถึงจันทร์ 5 ต.ค. 16:00; แบบ 24 ชม. ถึงเสาร์ 3 ต.ค. 16:00 หากไม่มีช่วงพัก SLA
4. งานที่เข้าวันหยุดเริ่มอายุงานรวมทันที แต่เวลาวันทำการเริ่มสะสมเมื่อเข้าสู่วันเปิดทำการถัดไป
5. แบบ continuous_24h นับวันหยุดด้วย แต่ยังหยุดเฉพาะช่วง waiting ตามกติกานาฬิกา GM
6. บันทึก policy และ calendar version ของงานเมื่อเริ่มใช้เกณฑ์นั้น การแก้ค่าเริ่มต้นใช้กับงานใหม่ ไม่เขียนประวัติหรือล้างการเกินกำหนดของงานเก่า
7. ค่า mock เป็นจันทร์–ศุกร์ ไม่มีวันหยุด Production ต้องให้ Admin ตรวจปฏิทินจริงครบ 5 สถานที่
8. การยืนยันหลัง GM เสร็จใช้ **72 ชั่วโมงต่อเนื่อง** ตามค่าเริ่มต้น Part 0 เพราะรายการที่ผู้ใช้ปรับเป็นวันทำการไม่ได้รวมขั้นตอนนี้ ระบุเป็นสมมติฐานที่ยังปรับได้ก่อน build โดยไม่กระทบกติกา stale/SLA

### 6.2 นาฬิกาที่ต้องแยกจากกัน

| นาฬิกา | เริ่ม/หยุด | ใช้ทำอะไร |
|---|---|---|
| SLA clock ของ GM | เริ่ม created_at หยุดทุกช่วง waiting และหยุดเมื่อถึง milestone ของ SLA; ช่วงยกเลิกไม่สะสมเวลาเพิ่ม หากเปิดกลับใช้ยอดเดิม | ประเมินทำตาม SLA; ประสานช่างหรือทำเสร็จตามชนิดเกณฑ์ |
| อายุงานรวม | created_at → ขณะนี้ หรือเวลาปิด/ยกเลิก ไม่หยุดช่วงรอหรือวันหยุด | ผู้ขอเห็นระยะเวลารวมของเรื่อง และเห็นระยะเวลาถึงปิดจริง |
| ระยะเวลารอรายฝ่าย | เวลาเข้ารอ → ออกจากรอ/เปลี่ยนฝ่ายที่รอ โดยนับเวลาจริงต่อเนื่อง | เวลารอสะสมและกราฟคอขวด |
| stale clock | จาก last_updated_at ใช้วันทำการของสถานที่ และเดินต่อระหว่าง waiting | ทำให้ GM ต้องอัปเดตหรือติดตามต่อภายในทุก 3 วันทำการ |

การพัก SLA ไม่ล้างการเกินกำหนดที่เกิดขึ้นแล้ว ไม่ล้างเวลาที่ใช้ไปก่อนรอ และไม่ทำให้อายุงานหรือ stale กลับเป็นศูนย์

### 6.3 รอผู้อื่นและติดตามแล้ว

- เข้า waiting ต้องเลือก waiting_on เป็นทีม/บุคคล/ผู้รับเหมา/หน่วยงานรัฐ และระบบกำหนด waiting_since
- ขณะหนึ่งมีฝ่ายที่รอหลักหนึ่งฝ่าย ทีมที่เกี่ยวข้องมีได้หลายทีม หากรอหลายฝ่าย ให้เลือกฝ่ายที่เป็นข้อจำกัดหลักและอธิบายฝ่ายอื่นในรายละเอียด ไม่เพิ่ม workflow งานย่อยคู่ขนานใน Phase 1
- เปลี่ยนจากรอฝ่าย A เป็นฝ่าย B ต้องปิดช่วง A และเปิดช่วง B แม้ status ยังเป็น waiting เพื่อไม่คิดเวลาปนกัน
- ปุ่ม “ติดตามแล้ว” ใช้ได้ในงานเว็บสถานะ waiting สำหรับ GM ที่มีสิทธิ์ แตะเดียวบันทึกผู้ทำ/เวลา/เหตุการณ์ใน history และปรับ last_updated_at
- “ติดตามแล้ว” หมายถึงผู้ใช้ยืนยันว่าได้ติดตามแล้ว ปุ่มนี้ไม่ส่งข้อความออกไปหาคู่กรณีโดยอัตโนมัติ
- ปุ่มดังกล่าวไม่เปลี่ยน waiting_on, waiting_since, status หรือ SLA clock และไม่ล้างเวลารอสะสม
- หมายเหตุการติดตามเป็นตัวเลือก ไม่บังคับทุกครั้งเพื่อรักษาการใช้งานหนึ่งแตะ
- เมื่อลากการ์ดเข้า waiting ต้องเปิดแบบสั้นให้กรอกฝ่ายที่รอ ถ้าไม่ครบคงสถานะเดิม

### 6.4 stale และ last_updated_at

- งาน queued / in_progress / waiting เป็น stale เมื่อเกิน 3 วันทำการนับจาก last_updated_at
- งานใหม่เริ่ม last_updated_at เท่ากับ created_at
- นับการรับงาน มอบหมาย เปลี่ยนสถานะ บันทึกการประสานช่าง บันทึกความคืบหน้าของ GM และ “ติดตามแล้ว” เป็นความคืบหน้า
- คอมเมนต์ใหม่จาก requester แจ้งให้ GM เห็นและเข้าประวัติ แต่ไม่รีเซ็ต stale เพื่อให้การรอคำตอบจาก GM ยังมองเห็นได้
- การเปิดดู sync ซ้ำ อัปเดตตัวนับ ส่ง notification หรือ scheduler ทำงาน ไม่รีเซ็ต stale
- ไม่คำนวณ stale สำหรับ completed / cancelled
- ข้อแลกเปลี่ยน: last_updated_at มีความหมายเป็นความคืบหน้าของ GM ไม่ใช่ทุกการแก้ข้อมูล ต้องแยกจากเวลาการแก้เชิงเทคนิคใน Part 6

### 6.5 การเสร็จ ยืนยัน ยกเลิก และเปิดกลับ

- GM กดเสร็จได้เมื่อมีสรุปผลการดำเนินการ อาจใช้ข้อความที่เตรียมไว้แล้ว หากยังไม่มีให้กรอกแบบสั้น
- งานที่มี requester: status = completed และแสดง “รอคุณยืนยัน” ตั้งเวลาปิดอัตโนมัติ 72 ชั่วโมงหลัง completed_at
- requester ยืนยัน: คง completed และบันทึก closed_at พร้อมชนิดการปิดว่า requester ยืนยัน
- ไม่ตอบภายในกำหนด: คง completed และบันทึก closed_at พร้อมชนิดการปิดอัตโนมัติ ห้ามรายงานว่าเป็นการยืนยันจากผู้ขอ
- ก่อนปิด requester เลือก “ยังไม่เรียบร้อย” พร้อมเหตุผลได้ งานกลับ in_progress และยกเลิกกำหนดปิดรอบเดิม
- หลังปิดแล้ว requester ติดต่อ GM ผ่านงานเดิมได้ GM เปิดกลับพร้อมเหตุผล ประวัติรอบปิดเดิมยังอยู่
- งานภายในไม่มี requester: เมื่อ GM กดเสร็จให้ completed และ closed_at ในคราวเดียว
- ยกเลิกโดย GM/Admin ต้องมีเหตุผล พนักงานขอยกเลิกผ่านคอมเมนต์ได้
- เปลี่ยนกลับจาก completed/cancelled โดย GM ต้องมีเหตุผลและคงหลักฐานเดิม ไม่ล้างเวลาที่เคยใช้หรือเหตุการณ์เกิน SLA
- SLA ที่วัดการทำเสร็จหยุดเมื่อ GM ทำเสร็จ ไม่เดินระหว่างรอยืนยัน หากเปิดกลับเพราะงานเดิมยังไม่เสร็จให้เดินต่อจากยอดเดิม
- SLA ที่วัดการประสานช่างจบเมื่อมีหลักฐานการประสาน การรับเรื่องเฉย ๆ หรือข้อความว่ากำลังติดต่อยังไม่ถือว่าถึง milestone
- กดซ้ำหรือคำสั่งจากเว็บและ Slack ชนกันต้องไม่สร้างสองเหตุการณ์ผลลัพธ์หรือสองงาน ระบบแสดงสถานะล่าสุด

### 6.6 SLA ที่ไม่ใช่งานไฟดับ/อินเทอร์เน็ตล่ม

Admin ตั้ง milestone และระยะเวลาตามประเภท หรือกำหนดรายกรณีพร้อมเหตุผลได้ งานที่ยังไม่กำหนด SLA แสดง “ยังไม่กำหนด SLA” แทนตัวเลขที่คาดเดา

การกำหนด SLA ครั้งแรกภายหลังเปิดงานยังใช้ created_at เป็นจุดเริ่ม และหักช่วง waiting ที่บันทึกไว้จริง ไม่เริ่มนับใหม่จากวันที่ตั้งเกณฑ์ เก็บวันที่กำหนด policy และเหตุผลให้ตรวจได้

การเปลี่ยนแม่แบบใช้กับงานใหม่ ส่วนการปรับเป้าหมายเฉพาะงานที่มี SLA แล้วต้องเก็บเป้าเดิม เหตุผล และผลที่เกิดไปแล้ว ผลรายงานทางการยังอ้างอิงเป้าเดิม; เป้าใหม่เป็นกำหนดวางแผนที่แสดงแยก เพื่อไม่ให้การขยายกำหนดเปลี่ยนงานที่พลาดแล้วเป็นผ่าน รายละเอียดข้อมูลกำหนดใน Part 6

### 6.7 นิยาม Dashboard และตัวเลข

Dashboard แสดง “ข้อมูล ณ เวลา…” และขอบเขตตามสิทธิ์เสมอ สัปดาห์เริ่มวันจันทร์ เดือน/ไตรมาสใช้ปฏิทินไทยใน timezone Asia/Bangkok

| รายการ | นิยาม |
|---|---|
| งานทั้งหมด | Request ที่สร้างในช่วง filter และอยู่ในขอบเขตสิทธิ์/คน/ประเภท/สถานที่ นับแต่ละ Request ครั้งเดียว |
| Donut 5 สถานะ | สถานะล่าสุด ณ เวลาที่ดู ของงานที่สร้างในช่วง filter; % เสร็จ = completed ÷ งานทั้งหมด รวม cancelled ในฐาน แสดงจำนวนฐาน |
| งานรายคนแยกสถานะ | งานใน cohort เดียวกัน จัดตามผู้รับผิดชอบปัจจุบัน มีช่อง “ยังไม่มอบหมาย” |
| แจ้งซ่อมตามสถานที่ | จำนวน maintenance ที่สร้างในช่วงเวลา แยกครบ 5 สถานที่ พร้อมค่า 0 ของสถานที่ที่ไม่มีงาน |
| รอทีมอื่น | งาน waiting ทั้งทีม/บุคคล/ผู้รับเหมา/หน่วยงานรัฐ ใน cohort เรียงช่วงรอปัจจุบันจากนานไปน้อย; ใช้ชื่อ “รอผู้อื่น” ให้ตรงสถานะ |
| ไม่อัปเดตเกิน 3 วันทำการ | งานใน 3 สถานะเปิดที่เข้าเกณฑ์ stale พร้อมลิงก์เปิดรายการ |
| % ทำตาม SLA | cohort งานสร้างในช่วง filter ที่มี SLA ประเมินได้: ถึง milestone แล้ว หรือเคยเกินกำหนดแล้ว ณ เวลารายงาน; ตัวตั้งคืองานถึง milestone ภายใน budget ที่หักช่วงรอ |
| งานยังรอผล SLA | งานมี SLA แต่ยังไม่ถึง milestone และยังไม่เคยเกินกำหนด แสดงจำนวนแยก ไม่ใส่เป็นผ่าน |
| ไม่มี SLA / Trello ที่ข้อมูลไม่พอ | แสดงจำนวนแยก ไม่รวมฐาน SLA และไม่ถือเป็นผ่าน; ถ้าฐานประเมินได้เป็น 0 แสดง “ยังประเมินไม่ได้” |
| ยกเลิกกับ SLA | ยกเลิกก่อนทราบผลไม่นำเข้าฐาน; เคยเกินกำหนดก่อนยกเลิกยังเป็นไม่ผ่าน; ถ้าวัดผลได้แล้วเก็บผลจริง |
| งานเข้า vs งานปิด รายสัปดาห์ | นับเหตุการณ์เปิดใหม่และปิดจริงในสัปดาห์นั้นจากทุก cohort; requester ยืนยัน/auto-close/งานภายในเสร็จนับเป็นปิดจริง ส่วนยกเลิกแยกให้เห็น |
| งานค้างในวงจรทั้งหมด | งานที่ยังไม่ปิดหรือยกเลิก รวม completed ที่รอยืนยัน; เปิดกลับจากงานที่ปิดแล้วเพิ่มกลับเข้าวงจร |
| กราฟรอใครบ่อยที่สุด | อันดับหลักเป็นจำนวน Request ไม่ซ้ำที่มีช่วงรอฝ่ายนั้นทับช่วง filter; แสดงเวลารอต่อเนื่องสะสมในช่วงนั้นและอายุงานรวมประกอบ |
| ความถี่และเวลารอ | งานหนึ่งรอฝ่ายเดิมหลายรอบนับเป็น 1 งานต่อฝ่าย แต่รวมระยะเวลาทุกช่วง; ไม่โยนอายุงานทั้งก้อนไปให้ผู้ที่รอล่าสุด |

กราฟงานเข้า/ปิดใช้ช่วงเวลาของ “เหตุการณ์” ส่วน donut/การ์ดสถิติใช้ช่วงเวลาของ “งานที่สร้าง” จึงต้องมีคำอธิบายฐานบน UI ไม่บังคับให้ยอดเท่ากัน

หากงานเดียวปิดและเปิดกลับหลายรอบ กราฟนับเหตุการณ์ปิดตามรอบ และมีจำนวนเปิดกลับประกอบเพื่ออธิบาย backlog:
งานที่ยังอยู่ในวงจรปลายช่วง = ต้นช่วง + เปิดใหม่ + เปิดกลับจากงานที่ปิด/ยกเลิก − ปิดจริง − ยกเลิก
การเปลี่ยนจาก completed ที่ยังรอยืนยันกลับ in_progress ไม่ใช่การเพิ่มงานเข้าวงจร เพราะงานนั้นยังไม่ปิด

### 6.8 Scorecard และแหล่งข้อมูล

| Tile | Phase 1 | แหล่งข้อมูล/นิยามที่ยืนยัน |

| เอกสารลงทะเบียนเกิน 3 วัน | “ยังไม่เชื่อมข้อมูล” พร้อมลิงก์ต้นทาง เป้า 0 | “รายการรับ-ส่งเอกสาร พัสดุ ประจำวัน”; เฉพาะ WH300 / Office 195; ลงทะเบียนช้ากว่าวันรับเกิน 3 วันทำการ หรือรับเกิน 3 วันทำการแล้วยังไม่ลงทะเบียน |

ข้อกำหนด:
- สาม Sheet เป็นแหล่งข้อมูลที่ผู้ใช้ระบุในบทสนทนา ยังไม่ได้อ่านคอลัมน์ เนื้อหา หรือลิงก์จริง
- Phase 1 ไม่คำนวณสาม tile หลังจาก Request เอกสารอย่างง่าย และไม่ให้กรอกเลข 0 เพื่อทำให้ดูครบ
- เมื่อยังไม่ได้ตั้ง URL ให้แสดง “ยังไม่ได้ตั้งลิงก์” เป็นข้อความรองของ “ยังไม่เชื่อมข้อมูล” ไม่สร้าง URL สมมติ
- Scorecard เป็น snapshot ณ เวลาเลือก ไม่หายไปเพียงเพราะคำขอถูกเปิดก่อนสัปดาห์ที่กำลังดู
- ค่าแรกเริ่มของ snapshot คือขณะนี้ และ export สำหรับรายสัปดาห์ใช้ปลายสัปดาห์ที่เลือก; สัปดาห์ปัจจุบันใช้เวลาขณะ export
- ไฟล์ CSV ระบุช่วงเวลา เวลา snapshot ขอบเขตสิทธิ์ ค่าตัวเลข และสถานะข้อมูล ถ้าข้อมูลไม่เชื่อมให้ช่องค่าตัวเลขว่างและระบุสถานะ
- ตัวเลข GM Scorecard ทางการใช้ขอบเขต GM รวมงานที่ GM มีสิทธิ์ ส่วน Viewer ได้ชุดที่เปิดเผยได้และต้องมีป้ายกำกับเพื่อไม่ให้สับสน
- ไม่สรุปว่าทรัพย์สินไม่ลงทะเบียนเป็น 0 จากการไม่พบแถวในทะเบียน ต้องมีบัญชีรายการที่ควรลงทะเบียนก่อน

### 6.9 Slack และ Trello

**Slack — P1/P2/P3**
- งานใหม่แจ้งผู้รับผิดชอบที่ผูกบัญชีไว้ ถ้ายังไม่มอบหมายให้ทีม GM ตามปลายทางที่ตั้งค่า
- ปุ่ม “รับเรื่อง” / “เสร็จแล้ว” ใช้สิทธิ์และกติกาชุดเดียวกับเว็บ ถ้าข้อมูลจำเป็นยังไม่ครบเปิดแบบสั้นก่อนบันทึก
- การรับเรื่องไม่ใช่การประสานช่าง และไม่หยุด SLA การประสานช่าง
- requester ได้แจ้งเมื่อสถานะเปลี่ยน ไม่ส่งซ้ำจาก webhook/retry เดิม
- digest เริ่มต้น 09:00 Asia/Bangkok ส่งให้ GM แต่ละคนในวันที่มีอย่างน้อยหนึ่งสถานที่ที่ตนรับผิดชอบเปิดทำการ รวม stale และ SLA ที่ใกล้ครบ โดย Admin ตั้งเวลาได้
- “ใกล้ครบ” เริ่มต้นหมายถึงเหลือ budget ไม่เกิน 25% และนาฬิกากำลังเดิน งาน waiting ที่พัก SLA ไม่แจ้งว่าเวลาที่พักกำลังจะหมด แต่ยังอยู่ในรายการรอ/stale ตามจริง
- งานลับใช้การแจ้งแบบจำกัดผู้รับ ข้อความในพื้นที่ทั่วไปไม่มีรายละเอียดงานลับ
- Slack ล่มหรือจับคู่ผู้ใช้ไม่ได้ งานยังบันทึกและติดตามในเว็บได้ แสดงปัญหาการส่งให้ GM ทราบโดยไม่ย้อนสถานะงาน

**Trello — P2/P4; milestone ท้ายสุด**
- รับเฉพาะงานภายในล้วน การ์ดที่มี requester หรือทีมเกี่ยวข้องนอก GM ไม่เข้าเส้นทาง Trello
- เว็บอ่านและสรุปพร้อมป้าย “จาก Trello” และปุ่ม “เปิดใน Trello”; ปิด drag/edit/Slack status actions ของการ์ดนำเข้า
- List map เข้าห้า status, มี type label ที่ใช้จำแนกงานหนึ่งค่า, label เสริมด้านทีมแยก namespace, Member map assignee, Due date เป็นกำหนดต้นทาง
- รายการผิดกติกา เช่น ไม่มี type/มีหลาย type/map คนไม่ได้/สถานะรอแต่ไม่มีฝ่ายที่รอ เข้ากล่อง “ยังไม่ระบุประเภท” พร้อมเหตุผลเฉพาะให้ GM/Admin ตรวจ ไม่เผยแพร่เป็นการ์ดสมบูรณ์
- งานนำเข้าต้องมีนโยบายการเปิดเผยที่ชัดเจนก่อนขึ้นบอร์ดพนักงาน ถ้ายังระบุไม่ได้ให้อยู่พื้นที่ตรวจสอบ
- Due date จาก Trello แสดงว่าเป็นกำหนดต้นทาง ไม่ถือเป็น SLA clock ที่พักได้ของเว็บ และไม่รวมเปอร์เซ็นต์ SLA ของเว็บเมื่อไม่มีประวัติรองรับ
- การ sync ไม่ตั้ง last_updated_at เป็นเวลาที่เพิ่งนำเข้าเฉย ๆ ถ้าประวัติต้นทางไม่พอ ให้แสดงว่าไม่ทราบเวลาอัปเดตที่ใช้วัด stale
- ไม่ทำการเขียนสถานะกลับ Trello; หากงานภายในเริ่มเกี่ยวข้องนอก GM ให้ GM สร้างคำขอเว็บที่อ้างอิงการ์ดต้นทางและยุติการติดตามซ้ำใน Trello ก่อนนับงานเว็บ ไม่เพิ่มปุ่มย้ายอัตโนมัติใน Phase 1

## 7. User stories และ acceptance criteria

ทุก story อ้างอิงกติกาส่วน 5–6 ร่วมกัน Given = เงื่อนไขตั้งต้น / When = การกระทำหรือเหตุการณ์ / Then = ผลที่ต้องตรวจได้

### US-01 เข้าสู่ระบบและเห็นข้อมูลตามสิทธิ์
**ในฐานะพนักงาน ฉันต้องการเข้าด้วยบัญชีบริษัทและเห็นเฉพาะข้อมูลที่เปิดให้ฉันได้** — P1, KR2.2

| Given | When | Then |
|---|---|---|
| บัญชี @tdfb.co ยืนยันแล้วและ active | เข้าสู่ระบบสำเร็จ | เห็นบอร์ดสรุปและเมนูตาม role |
| บัญชีนอกโดเมน/ถูกปิดใช้งาน | เข้าผ่านหน้าเว็บหรือลิงก์ตรง | ไม่ได้รับข้อมูลคำขอหรือไฟล์ |
| พนักงานไม่มีความสัมพันธ์กับงาน | เปิด URL รายละเอียดหรือเรียกข้อมูลโดยตรง | ปฏิเสธรายละเอียด แม้มองเห็นสรุปบนบอร์ด |
| Viewer เปิด Dashboard | มีงานลับอยู่ในข้อมูล | เห็นทุก widget ในขอบเขตที่เปิดเผยและจำนวนงานภายในรวม ไม่มีรายละเอียดงานลับ |

### US-02 หน้าแรก ค้นหา และติดต่อทีม
**ในฐานะพนักงาน ฉันต้องการรู้ว่าจะเริ่มเรื่องตรงไหนและทีมกำลังทำอะไร** — P1, P3, KR2.2

| Given | When | Then |
|---|---|---|
| เข้าสู่ระบบแล้ว | เปิดหน้าแรก | เห็นค้นหา ปุ่มแจ้งซ่อม/ขอเอกสาร/ส่งเอกสาร/ถามทีม GM งานปัจจุบันของ 3 คน บอร์ดย่อ และประกาศ |
| ค้นหาหมายเลขหรือคำในชื่องาน | มีงานตรงคำค้นหลายสิทธิ์ | ผลลัพธ์แสดงเฉพาะข้อมูลที่ผู้ใช้มีสิทธิ์ ไม่มีชื่อหรือ snippet งานลับ |
| ต้องการถามทีม | เปิด “ถามทีม GM” | เห็นคนดูแลเรื่อง ช่องทางติดต่อ FAQ และทางเปิดคำขอ ไม่สร้างแชตบอตเพิ่ม |
| งานปัจจุบันของบุคคลเป็นงานลับ | ดู avatar บนหน้าแรก | แสดงเพียงข้อมูลรวม “งานภายใน” ไม่มีชื่องานลับ |
| Admin ยังไม่ตั้งลิงก์ expense | แตะส่วนบริการการเงิน | เห็นข้อความว่ายังไม่ได้ตั้งลิงก์ ไม่มีลิงก์สมมติ |

### US-03 แจ้งซ่อมผ่านมือถือและ QR
**ในฐานะพนักงาน ฉันต้องการแจ้งอาการได้ภายใน 4 ขั้น** — P1, KR2.2

| Given | When | Then |
|---|---|---|
| เลือกแจ้งซ่อม | กรอกสถานที่ → บริเวณ → อาการ → รูป/รายละเอียด | ส่งได้ในไม่เกิน 4 ขั้น รูปเป็นตัวเลือก |
| สแกน QR สถานที่/บริเวณที่ใช้งานได้ | เข้าแบบฟอร์ม | เติมสถานที่และบริเวณให้อัตโนมัติ พร้อมให้ผู้ใช้ตรวจหรือเปลี่ยน |
| QR หมดอายุ ถูกปิด หรือไม่พบ | เปิดฟอร์ม | แจ้งเหตุและให้เลือกสถานที่เองได้ |
| เลือก “อื่น ๆ” | ส่งโดยไม่มีรายละเอียดอาการ | ชี้ช่องที่ต้องเติมและคงข้อมูลเดิม |
| กดส่งซ้ำจากเครือข่ายช้า | ระบบยืนยันบันทึก | ได้ Request เดียว เลขอ้างอิงเดียว สถานะ queued และเห็นในคำขอของฉัน |

หมวดอาการตั้งต้น: แอร์, หลอดไฟ, ไฟดับ, อินเทอร์เน็ต, ห้องน้ำ, ซิงค์, ลิฟท์, กล้องวงจรปิด, เครื่องฟอกอากาศ, เครื่องปริ้นท์, โต๊ะ/โต๊ะแพ็ค, Shelf, ตู้ไฟ, อื่นๆ

### US-04 รับคำขอเอกสารและส่งเอกสารใน Phase 1
**ในฐานะพนักงาน ฉันต้องการส่งเรื่องเอกสารและติดตามได้ผ่านช่องทางเดียว** — P1, KR2.2

| Given | When | Then |
|---|---|---|
| เลือกขอเอกสารหรือส่งเอกสาร | ระบุเรื่อง สถานที่ รายละเอียด และลิงก์ Drive ถ้ามี | เกิด document_request หรือ document_intake ใน Request เดียวกันกับบอร์ด |

### US-05 คำขอของฉันและการสนทนาในงาน
**ในฐานะผู้ขอ ฉันต้องการเห็นว่าใครทำ กำลังรอใคร และเรื่องนี้ใช้เวลามาเท่าไร** — P1, P3, KR2.2

| Given | When | Then |
|---|---|---|
| เป็น requester ของงาน | เปิดรายละเอียด | เห็นสถานะ ผู้รับผิดชอบ อายุงานรวม ช่วงรอ timeline คอมเมนต์ รูป และลิงก์ที่มีสิทธิ์ |
| เป็นสมาชิกทีมที่เกี่ยวข้องและมีสิทธิ์ | เปิดงาน | อ่านรายละเอียดและแสดงความคิดเห็นได้ ไม่มีสิทธิ์เปลี่ยนสถานะของ GM |
| คอมเมนต์หรือแนบรูปแล้วบันทึกไม่สำเร็จ | ระบบตอบข้อผิดพลาด | ข้อความที่พิมพ์ยังอยู่ มีทางลองใหม่ และไม่แสดงว่าบันทึกสำเร็จ |
| requester เพิ่มคอมเมนต์ในงาน stale | เปิดบอร์ด GM | GM เห็นกิจกรรมใหม่ แต่ป้าย stale คงอยู่จน GM อัปเดตความคืบหน้า |

### US-06 GM รับงาน มอบหมาย และบันทึกการประสาน
**ในฐานะ GM ฉันต้องการรับงานและบันทึกสิ่งที่ทำจริงโดยใช้ขั้นตอนน้อย** — P1, P2, KR2.2

| Given | When | Then |
|---|---|---|
| มีงานเว็บ queued | GM กดรับเรื่อง | ตั้ง in_progress และผู้รับผิดชอบตามกติกา พร้อม history และอัปเดตผู้ชมที่มีสิทธิ์ |
| งานไฟดับมี SLA ประสานช่าง | GM กดรับเรื่องอย่างเดียว | SLA ยังเดินและยังไม่ถือว่าทำตามเป้าสำเร็จ |
| GM ได้ประสานช่างแล้ว | กดบันทึกพร้อมผู้ที่ประสาน/ข้อมูลขั้นต่ำ | เก็บเหตุการณ์และเวลาเพื่อวัด SLA โดย status ซ่อมยังเป็นกำลังทำหรือรอผู้อื่นได้ |
| มี GM สองคนรับงานชนกัน | ระบบรับคำสั่ง | บันทึกผลที่สอดคล้องเพียงครั้งเดียว อีกคนเห็นข้อมูลล่าสุด |

### US-07 รอผู้อื่นและติดตามแล้ว
**ในฐานะ GM ฉันต้องการแสดงคอขวดและติดตามงานรออย่างสม่ำเสมอ** — P2, P3, KR2.2

| Given | When | Then |
|---|---|---|
| งานกำลังทำ | เปลี่ยนเป็น waiting โดยไม่เลือกฝ่าย | ไม่บันทึกและบอกข้อมูลที่ต้องเพิ่ม |
| เลือกฝ่ายครบแล้ว | ยืนยันรอผู้อื่น | เปิดช่วงรอ หยุด SLA ของ GM และให้อายุงาน/stale เดินต่อ |
| งานรอเกิน 3 วันทำการ | GM กด “ติดตามแล้ว” | บันทึก history รีเซ็ต stale clock แต่ไม่รีเซ็ตเวลารอหรือเริ่ม SLA |
| รอฝ่าย A แล้วต้องรอฝ่าย B ต่อ | เปลี่ยนฝ่ายหลัก | เก็บช่วง A ไว้ เปิดช่วง B ใหม่ และกราฟรวมระยะเวลาของแต่ละฝ่ายถูกต้อง |

### US-08 เสร็จ ยืนยัน และปิดอัตโนมัติ
**ในฐานะผู้ขอ ฉันต้องการตรวจว่าปัญหาเรียบร้อยจริงก่อนปิดเรื่อง** — P1, P2, KR2.2

| Given | When | Then |
|---|---|---|
| GM มีผลดำเนินการแล้ว | กดเสร็จ | completed พร้อม “รอคุณยืนยัน” และแจ้ง requester |
| อยู่ระหว่างรอยืนยัน | requester ยืนยัน | บันทึกการปิดโดยผู้ขอและหยุดอายุงานรวม |
| ไม่มีการตอบกลับครบ 72 ชั่วโมง | งานยังเป็น completed รอบเดิม | ปิดอัตโนมัติครั้งเดียวและระบุว่าเป็น auto-close |
| requester แจ้งยังไม่เรียบร้อยก่อนกำหนด | ใส่เหตุผลและส่ง | กลับ in_progress ปิดกำหนด auto-close รอบเก่า และประวัติคงอยู่ |
| ระบบกำลังปิดอัตโนมัติพร้อมกับมีการเปิดกลับ | ตรวจสถานะล่าสุด | งานที่เปิดกลับแล้วไม่ถูกปิดจากกำหนดเก่า |

### US-09 ยกเลิกและย้อนสถานะ
**ในฐานะ GM ฉันต้องการแก้สถานะได้โดยไม่เสียประวัติ** — P2, KR2.2

| Given | When | Then |
|---|---|---|
| งานใดก็ตามที่ GM มีสิทธิ์ | กดยกเลิกหรือเปิดกลับจากเสร็จ/ยกเลิก | ต้องใส่เหตุผลก่อนบันทึก |
| งานเคยเกิน SLA | ยกเลิกหรือย้อนสถานะ | เหตุการณ์เกินกำหนดและเวลาที่ใช้แล้วไม่หาย |
| งานภายในไม่มี requester | GM กดเสร็จ | ปิดจริงทันทีโดยไม่รอ 72 ชั่วโมง |

### US-10 บอร์ดร่วมและมุมมองทีม
**ในฐานะพนักงาน ฉันต้องการเห็นภาพงาน GM; ในฐานะ GM ฉันต้องจัดคิวได้จากบอร์ดเดียว** — P1, P2, P3, KR2.2

| Given | When | Then |
|---|---|---|
| พนักงานเปิดบอร์ด | โหลดสำเร็จ | เห็น 5 สถานะและสรุปงานตามสิทธิ์ |
| GM เลือกมุมมองตามคน/สถานที่ | ใช้ filter คน ประเภท สถานที่ ทีมที่เกี่ยวข้อง | งานและจำนวนตรงกับ filter และยังมีทางเห็นงานไม่มอบหมาย |
| GM ย้ายการ์ดเว็บ | ใช้ drag หรือปุ่มเปลี่ยนสถานะ | ใช้กติกาเดียวกัน รอผู้อื่น/ยกเลิกเปิดแบบข้อมูลจำเป็น |
| ข้อมูลเปลี่ยนขณะกำลังกรอก | listener ได้ข้อมูลใหม่ | ไม่ล้างฟอร์มที่กำลังแก้ และแจ้งเมื่อมีความขัดแย้ง |
| มีงาน stale | แสดงการ์ด | มีป้ายและการเน้นที่อ่านได้ ไม่พึ่งการทำสีซีดอย่างเดียว |

### US-11 Dashboard
**ในฐานะ GM/Viewer ฉันต้องการเห็นภาระงานและคอขวดจากนิยามที่ตรวจได้** — P2, P3, P4, KR2.2

| Given | When | Then |
|---|---|---|
| เปิด Dashboard | เลือกสัปดาห์/เดือน/ไตรมาส คน ประเภท สถานที่ | metric cards, donut, งานรายคน, งานซ่อม 5 สถานที่, รายการรอ, งานเข้า/ปิด และคอขวดใช้ filter ตามนิยาม |
| งานไม่มี SLA หรือยังไม่ถึงจุดประเมิน | คำนวณเปอร์เซ็นต์ | แยกจำนวนที่ไม่อยู่ในฐาน ไม่ถือเป็นผ่าน และฐาน 0 แสดง “ยังประเมินไม่ได้” |
| งานรอหลายฝ่ายต่อกัน | ดูกราฟคอขวด | เวลาที่รอแต่ละฝ่ายมาจากช่วงจริง ไม่ใช่อายุงานทั้งหมด |
| Viewer ใช้ filter หรือ export | มีงานลับในระบบ | ไม่ได้ชื่อ แถว หรือการแจกแจงที่เปิดรายละเอียดงานลับ |
| ไม่มีงานตาม filter | เปิดกราฟ | เห็น empty state และคำอธิบาย ไม่ทำให้เข้าใจว่าการโหลดล้มเหลว |

### US-12 Scorecard และ CSV
**ในฐานะ GM ฉันต้องการตัวเลขรายสัปดาห์โดยไม่ต้องนับการ์ดเอง** — P4, KR2.2

| Given | When | Then |
|---|---|---|
| มี maintenance เปิดอยู่ 3 งาน: queued, waiting และ completed รอยืนยัน | ดูงานซ่อมค้าง | แสดง 2 และแสดงรอยืนยันแยก |
| มีงานซ่อมเก่าตั้งแต่ก่อนสัปดาห์ที่เลือกยังไม่เสร็จ | ดู snapshot ปลายสัปดาห์ | งานเก่ายังถูกนับตามสถานะ ณ ตอนนั้น |
| ยังไม่เชื่อมทะเบียน Phase 2 | ดูสาม tile ที่เหลือหรือ CSV | แสดง “ยังไม่เชื่อมข้อมูล”; ตัวเลขว่างใน CSV พร้อมสถานะและลิงก์ที่ตั้งไว้ |
| ส่งออกรายสัปดาห์ | เปิดไฟล์ในโปรแกรมตาราง | ภาษาไทยอ่านได้ มีช่วงเวลา เวลา snapshot และขอบเขตข้อมูลครบ |

### US-13 Admin ตั้งค่าสถานที่ ปฏิทิน SLA และผู้ใช้
**ในฐานะ GM Admin ฉันต้องการดูแลค่าธุรกิจได้เอง** — P1, P2, KR2.2

| Given | When | Then |
|---|---|---|
| เป็น GM Admin | เพิ่ม/แก้บริเวณใต้สถานที่หรือสร้าง QR | บริเวณผูกสถานที่ถูกต้อง และ QR เปิดฟอร์มที่กรอกค่าไว้ |
| บริเวณเคยมีงาน | ปิดใช้งานบริเวณ | งานเก่ายังอ่านตำแหน่งเดิมได้ และงานใหม่เลือกบริเวณนั้นไม่ได้ |
| ปฏิทิน WH300 เปิดเสาร์ แต่ออฟฟิศปิด | คำนวณงานเวลาเริ่มและ policy เดียวกัน | SLA/stale/ทะเบียนใช้ปฏิทินของสถานที่ตัวเอง |
| Admin เปลี่ยนค่าเริ่มต้น SLA หรือวันหยุด | มีงานเก่าที่กำลังดำเนินการ | งานเก่าเก็บ policy/calendar เดิมและประวัติ งานใหม่ใช้ค่าใหม่ |
| ผู้ใช้ไม่มี role gm_admin | พยายามแก้สิทธิ์ตนเองหรือตั้งค่า | ระบบปฏิเสธจากฝั่งที่ควบคุมข้อมูล |

### US-14 Slack
**ในฐานะ GM ฉันต้องการทำรายการพื้นฐานจาก Slack และเห็นงานที่ต้องติดตาม** — P1, P2, P3, KR2.2

| Given | When | Then |
|---|---|---|
| บัญชี Slack จับคู่พนักงานที่มีสิทธิ์แล้ว | กดรับเรื่อง/เสร็จแล้ว | ใช้กติกาเดียวกับเว็บ มีผลครั้งเดียวและ history ระบุแหล่งคำสั่ง |
| ผู้ไม่มีสิทธิ์ หรือเป็นงาน read-only จาก Trello | กด action | ไม่เปลี่ยนงาน แจ้งเหตุหรือให้เปิด Trello |
| ถึงเวลา digest | มี stale หรือ SLA ใกล้ครบตามเกณฑ์ | ส่งเฉพาะรายการที่ผู้รับมีสิทธิ์ พร้อมทางเปิดงาน |
| Slack ใช้งานไม่ได้ | GM ทำรายการจากเว็บ | งานสำเร็จได้ และแสดงสถานะการแจ้งเตือนแยกจากผลบันทึกงาน |

### US-15 Trello แบบเลื่อนได้
**ในฐานะ GM ฉันต้องการเห็นงานภายในจาก Trello โดยไม่ต้องอัปเดตซ้ำ** — P2, P4, KR2.2

| Given | When | Then |
|---|---|---|
| เป็นงานภายในล้วนและ mapping ถูกต้อง | webhook แจ้งการเปลี่ยน | เว็บอัปเดตการ์ดเดิมพร้อมป้าย “จาก Trello” ไม่มีคำขอซ้ำ |
| เป็นการ์ดนำเข้า | พยายามย้ายหรือแก้บนเว็บ/Slack | แสดง read-only และปุ่มเปิดต้นทาง |
| ไม่มี type หรือผิดเงื่อนไขอื่น | sync เข้ามา | อยู่ในกล่อง “ยังไม่ระบุประเภท” พร้อมเหตุผลให้ GM ตรวจ |
| Trello ยังไม่พร้อมตาม milestone | เปิดใช้ maintenance | ระบบหลักเปิดใช้ได้โดยไม่รอ Trello |
| มี Due date แต่ไม่มีประวัติพัก SLA | เปิด Dashboard | ไม่เอากำหนดต้นทางมาปนเปอร์เซ็นต์ SLA ของเว็บ |

### US-16 ความสะดวกบนมือถือและสถานะผิดพลาด
**ในฐานะพนักงานทุกวัย ฉันต้องใช้ระบบได้แม้ไม่ถนัดเทคโนโลยีหรือเครือข่ายสะดุด** — P1, P2, KR2.2

| Given | When | Then |
|---|---|---|
| ใช้มือถือ | ใช้หน้าฝั่ง requester | ตัวอักษร body ≥ 16px ปุ่มเป้าหมาย ≥ 44px ภาษาไทยอ่านครบ และไม่ต้องเลื่อนแนวนอนในฟอร์ม |
| เปิดหน้าใดก็ตาม | อยู่ใน empty/loading/error | มีข้อความหรือ skeleton และทางแก้/ลองใหม่ตามบริบท |
| เปิด reduced motion | เปลี่ยนหน้า สถานะ หรือกราฟ | แสดงผลทันทีโดยไม่เคลื่อนไหว รวม skeleton แบบนิ่ง |
| การเชื่อมต่อสดหลุด | ดูบอร์ด | เห็นว่าข้อมูลอาจไม่ล่าสุด ไม่แสดงว่า real-time ยังปกติ |
| อุปกรณ์รองรับการติดตั้ง PWA | เพิ่มไอคอน | เปิดกลับเข้าเว็บได้; การติดตั้งไม่สัญญาว่าทำรายการแบบ offline ได้ |
| คนใช้ keyboard หรือไม่สะดวก drag | เปลี่ยนสถานะ/ใช้ filter | ทำงานผ่านปุ่มและ focus ที่มองเห็นได้ |

### US-17 ทะเบียนเอกสาร — Phase 2
**ในฐานะ GM ฉันต้องการเห็นเอกสารที่ลงทะเบียนช้าและงานต่ออายุที่ค้างจากข้อมูลจริง** — P1, P4, KR2.2

| Given | When | Then |
|---|---|---|
| รายการเอกสารมีวันรับและสถานที่ WH300/Office 195 | ลงทะเบียนภายหลังเกิน 3 วันทำการ หรือยังไม่ลงทะเบียนเมื่อเกินเกณฑ์ | ติดสถานะผิดเกณฑ์ตามปฏิทินสถานที่ |
| ลงทะเบียนตรงขอบเวลา 3 วันทำการพอดี | ประเมินรายการ | ยังไม่จัดเป็น “เกิน 3 วัน” |
| มีเอกสารที่เข้าเงื่อนไขช้าหนึ่งรายการ | สร้างตัวเลขในช่วงรายงาน | นับรายการครั้งเดียว ไม่บวกซ้ำทั้งกลุ่มช้าและยังไม่ลงทะเบียน |
| เอกสารมีวันหมดอายุและช่วงแจ้งเตือนที่กำหนด | เข้าเกณฑ์เตือน | เกิดงานต่ออายุ/การเตือนที่อ้างอิงทะเบียนเดิม ไม่สร้างงานซ้ำทุกวัน |

นิยามช่วงรายงานของ “เคยลงทะเบียนช้า” เทียบกับ “ค้างลงทะเบียน ณ เวลาใด” และเกณฑ์สัญญารอ/ต่ออายุค้างต้องยืนยันจากคอลัมน์จริงใน Phase 2 ไม่อ้างว่า Phase 1 มีข้อมูลนี้แล้ว

### US-18 ทะเบียนทรัพย์สิน — Phase 2
**ในฐานะ GM/พนักงาน ฉันต้องการค้นทรัพย์สินและเชื่อมประวัติซ่อมได้** — P1, P4, KR2.2

| มีบัญชีรายการรับเข้าที่ควรลงทะเบียน | เทียบกับทะเบียนที่ลงแล้ว | นับรายการขาดทะเบียนด้วยรหัสอ้างอิงที่ตรวจสอบซ้ำได้ |

## 8. คุณภาพและเกณฑ์เปิดใช้

1. ตรวจเส้นทางแจ้งซ่อมตั้งแต่ QR/แบบฟอร์มถึงยืนยัน/auto-close ครบ 5 สถานที่ รวมงาน GM ช่วยเปิดแทนผู้ขอ
2. ตรวจสิทธิ์บอร์ดสรุป รายละเอียด งานลับ ค้นหา รูป/ไฟล์ ลิงก์ตรง และ CSV ด้วยบทบาทที่ต่างกัน
3. ตรวจปฏิทิน 2 สถานที่ที่วันทำการต่างกัน วันหยุด งานเปิดในวันหยุด และงานที่สลับ waiting หลายครั้ง
4. ตรวจ stale ที่ยังเดินระหว่าง waiting และ “ติดตามแล้ว” ที่ไม่ล้างเวลารอหรือประวัติ
5. ตรวจ milestone ประสานช่างแยกจากรับเรื่อง/ซ่อมเสร็จ และยกเลิกหรือเปิดกลับแล้วไม่ลบการเกิน SLA
6. ตรวจข้อมูล Dashboard กับชุดตัวอย่างที่มีงานไม่มี SLA ฐาน 0 งานลับ งานเก่าค้าง งานรอยืนยัน งานเปิดกลับ และหลายฝ่ายที่รอ
7. ตรวจคำสั่งซ้ำ ข้อมูลชน และ scheduler รอบเก่าไม่ปิดงานที่เปิดกลับแล้ว
8. ตรวจ empty/loading/error ทุกหน้า เป้าหมายการแตะ keyboard contrast ภาษาไทย และ reduced motion; ค่าสีและ motion ระบุใน Part 4
9. เป้าหมายการสดของข้อมูลในการทดสอบเครือข่ายปกติ: อย่างน้อย 95% ของการเปลี่ยนที่ยืนยันแล้วเห็นบนอีกอุปกรณ์ภายใน 5 วินาที เป้าหมายนี้เป็นเกณฑ์ทดสอบ ไม่ใช่คำรับประกันเครือข่ายทุกสาขา
10. Slack และ Trello ขัดข้องต้องไม่ทำให้คำขอบนเว็บสูญหาย ทั้งนี้ Trello ไม่เป็น release gate ของ maintenance
11. Production ใช้ปฏิทิน สถานที่ ผู้ใช้/ทีม และลิงก์จริงที่ Admin ตรวจแล้ว รูปทีมจริงใช้เมื่อได้รับแล้ว ช่วงต้นใช้ชื่อย่อได้ตาม assumption ที่รับไว้
12. Phase 1 จบเมื่อขอบเขตหลักและ Slack ผ่านเกณฑ์ครบ Trello ระบุสถานะส่งมอบหรือเลื่อนไป Phase 2 อย่างตรงไปตรงมา

## 9. การตัดสินใจและข้อแลกเปลี่ยน

| การตัดสินใจ | เหตุผล | ข้อแลกเปลี่ยน |
|---|---|---|
| Request เดียวสำหรับทุกงาน | บอร์ดและรายงานใช้ข้อมูลร่วมกัน | ต้องแยก type/category/สิทธิ์ชัดเจน |
| รับเอกสารเป็นคำขอใน Phase 1 | พนักงานเริ่มใช้ช่องทางเดียวได้ | ยังไม่ใช่การลงทะเบียนในชีทหรือทะเบียนเต็ม |
| หยุด SLA ขณะรอ แต่แสดงเวลารอต่อเนื่อง | แยกเวลาที่ GM ควบคุมได้กับประสบการณ์ผู้ขอ | SLA อาจดูดีแม้งานค้างนาน จึงต้องอ่านคู่ waiting/stale/อายุงาน |
| 5 สถานะและแยกการปิดจากการเสร็จ | รักษาบอร์ดง่ายและมีการยืนยัน | ต้องติดป้าย “รอคุณยืนยัน” และแยกตัวเลขซ่อมค้างกับงานยังไม่ปิด |
| ทุกพนักงานเห็นบอร์ดสรุป | เห็นงานและคิวร่วมกัน | ต้องมีข้อมูลสรุปที่ไม่เปิดรายละเอียดเกินสิทธิ์ |
| ใช้วันทำการแบบเต็มวันที่เปิด | รองรับปฏิทินรายสถานที่โดยไม่เพิ่มระบบกะ | กำหนดอาจตรงเวลานอกชั่วโมงออฟฟิศ; ถ้าต้องใช้เวลาทำงานจริงต้องขยายข้อกำหนดก่อน build |
| รายงาน SLA เฉพาะงานประเมินได้ | ไม่สร้างเปอร์เซ็นต์ผ่านจากงานไม่มีเกณฑ์ | ต้องแสดงจำนวนรอผลและไม่มี SLA ประกอบ |
| Trello read-only และทำท้าย | ลดความขัดแย้งและไม่ขวางแจ้งซ่อม | งานนำเข้าบางส่วนต้องเปิดแก้ที่ Trello |
| Scorecard 3 ตัวแสดงยังไม่เชื่อม | ตัวเลขซื่อตรงต่อแหล่งข้อมูล | ยังต้องเปิดชีทต้นทางระหว่าง Phase 1 |
| งานทั่วไปใช้หนึ่งแตะ งานที่ต้องมีเหตุผลใช้แบบสั้น | ลดภาระการอัปเดตโดยยังมีหลักฐาน | ไม่ใช่ทุกสถานะที่เปลี่ยนได้ด้วยแตะเดียวเสมอ |

## 10. สิ่งที่ต้องเติมก่อนสร้างระบบจริง

รายการนี้เป็นข้อมูลเตรียม build ไม่ใช่คำถามที่ขวาง Part 2:
- ปฏิทินจริงของทั้ง 5 สถานที่ และข้อยืนยันนิยามวันทำการแบบเต็มวัน
- ผู้ถือ role GM Admin, รายชื่อทีม/สมาชิก และตัวตนที่ใช้จับคู่ Google กับ Slack
- ลิงก์จริงของ Sheet ทั้ง 3, แอป expense, ช่องทางติดต่อทีม และรูปทีมเมื่อพร้อม
- สิทธิ์โครงการ Firebase, Google Workspace และ Slack ที่ใช้สำหรับการพัฒนา/เชื่อมต่อ; Trello เตรียมตาม milestone ท้าย
- ช่วงยืนยันงาน 72 ชั่วโมงที่ยังคงเป็น assumption และเป้าหมาย pilot ที่ยังเป็นข้อเสนอ
- โครงคอลัมน์ชีทและรายการต้นทางที่ใช้เทียบทรัพย์สินขาดทะเบียน เตรียมก่อน Phase 2

ไม่มีการเพิ่มข้อเสนอเพิ่มเติมเข้า scope อัตโนมัติใน Part นี้ ทุกความสามารถด้านบนอ้างอิง P1–P4 หรือ KR2.2 และลิงก์ expense จำกัดอยู่ที่การเข้าถึงเครื่องมือของ KR2.1
