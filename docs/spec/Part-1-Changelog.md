## C2. GM สร้างงานเอง และเปิดแทนผู้ขอ (เพิ่ม US-19, US-20; ปรับ §5.1)
- เปลี่ยนชื่อ type internal_task → gm_task (งานที่ GM เริ่มเอง ทั้งภายในล้วนและข้ามทีม)
  แทนที่ทุกจุด งานจาก Trello ใช้ type gm_task + source = trello
- เพิ่ม field: created_by_id (ผู้กดสร้าง), origin = requester | gm_on_behalf | gm_initiated
  requester_id คือผู้ขอจริงเท่านั้น gm_task ไม่มี requester_id
- gm_task: GM กดเสร็จ = completed + closed_at ทันที (ตามกติกางานภายในใน §6.5 เดิม)

| Given | When | Then |

## C3. แจ้งฝ่ายที่ถูกรอ (ปรับ §6.3, §6.9, US-07)
- waiting_on เก็บเป็น { kind: person | team | contractor | government | other,
  person_id?, team_label?, name? }
- kind = person: ค่าเริ่มต้นส่ง Slack DM พร้อมลิงก์งาน GM ปิดตัวเลือกได้ก่อนยืนยัน
- kind = team: เลือกผู้ติดต่อของทีมนั้น 1-3 คนได้ถ้าต้องการแจ้ง (ไม่บังคับ) team_label ยังบันทึกเพื่อรายงาน
- kind = contractor / government / other: ไม่ส่งแจ้งเตือน
- ผู้ที่ถูกแจ้งถูกเพิ่มเป็น related person อัตโนมัติเพื่อเปิดลิงก์ได้ และแสดงให้ GM เห็นก่อนยืนยัน
- งานลับ: ข้อความ Slack ไม่มีรายละเอียดงาน และการเพิ่ม related person ต้องยืนยันแยก
- "ติดตามแล้ว" เพิ่มตัวเลือก "ส่งเตือนอีกครั้ง" สำหรับ person/team ที่มีผู้ติดต่อ
  จำกัด 1 ครั้งต่อวันทำการต่องาน บันทึก reminded_at ใน history
- ส่งไม่สำเร็จ (จับคู่ Slack ไม่ได้ / Slack ล่ม) งานยังบันทึกได้ และแสดงสถานะการส่งให้ GM เห็น
- US-07 เพิ่มแถว:
  | รอพนักงานภายใน | ยืนยันรอผู้อื่นโดยเปิดการแจ้ง | ผู้ถูกรอได้ DM ครั้งเดียว และเปิดงานจากลิงก์ได้ |

## C4. ผู้เกี่ยวข้องรายบุคคล (แทน related_team_ids ใน §5.1, ปรับ §5.2, US-05)
- related_person_ids: ได้สิทธิ์ดูรายละเอียดและคอมเมนต์ ไม่มีสิทธิ์เปลี่ยนสถานะ
- team_labels: ใช้กับรายงาน / filter / กราฟคอขวดเท่านั้น ไม่ให้สิทธิ์ใดๆ
- ตัด "สมาชิกทีมที่ Admin จัดการ" ออกจาก Phase 1 (§5.2 ข้อกำหนดข้อที่ 7)
- ทุกจุดที่เขียนว่า "ทีมที่เกี่ยวข้อง" ในเชิงสิทธิ์ ให้อ่านเป็น "ผู้เกี่ยวข้อง (รายบุคคล)"

## C5. ยืนยันหลังเสร็จ = 3 วันทำการ (แทน §6.1 ข้อ 8, ปรับ §6.5, US-08, US-09, §10)
- auto_close_due_at = completed_at + 3 วันทำการ ตามปฏิทินสถานที่ของงาน
- งานที่ไม่มีสถานที่ หรืออยู่ในด่าน A ที่ยังไม่มีปฏิทินรายสถานที่ ใช้ปฏิทินบริษัท
  (จ-ศ + วันหยุดที่ Admin ใส่)
- ใช้นิยามวันทำการเดียวกับ §6.1 ข้อ 2-3 (สะสม 24 ชม. บนวันที่เปิดทำการ)
- US-08: "ไม่มีการตอบกลับครบ 72 ชั่วโมง" → "ไม่มีการตอบกลับครบ 3 วันทำการ"
- US-09: "ปิดจริงทันทีโดยไม่รอ 72 ชั่วโมง" → "ปิดจริงทันทีโดยไม่รอการยืนยัน"
- ลบรายการ 72 ชั่วโมงออกจาก §10
- Production ต้องใส่วันหยุดช่วงปลายปี 2026 – ต้นปี 2027 ก่อนเปิด pilot

## C6. ธงลับเริ่มต้น (แทน §5.2 ข้อกำหนดข้อสุดท้าย, ปรับ US-04)
- เปิดธงลับเป็นค่าเริ่มต้นเฉพาะ: เรื่องสัญญา และเรื่องบุคคล (เก็บเหตุผลใน sensitivity_reason)
- เอกสารบริษัททั่วไป (เช่น ภ.พ.20, หนังสือรับรองบริษัท) ไม่ลับโดยค่าเริ่มต้น
- ทุกงานต้องมีชื่อบนบอร์ดที่เปิดเผยได้ (summary_title) ฟอร์มแนะนำให้ใช้ชื่อกลางๆ
  เช่น "ขอเอกสารบริษัท — ทีมบัญชี" ไม่ใส่เลขเอกสารหรือข้อมูลส่วนบุคคลในชื่อ
- การปลดธงโดย GM Admin พร้อมเหตุผล คงเดิม
- US-04 แถว 2: "เป็นเอกสารสัญญา บริษัท หรือเรื่องบุคคล" → "เป็นเรื่องสัญญาหรือเรื่องบุคคล"

## C7. งานปัจจุบันและสถานะของทีม GM บนหน้าแรก (เพิ่ม US-21, ปรับ US-02)
- profile ของ GM เก็บ: focus_request_id (ปักได้ 1 งาน), presence_status, presence_updated_at
- presence_status: อยู่ WH300 / อยู่ FAC16 / อยู่ FAC17 / อยู่ Office 195 / อยู่ Cafe 222,
  ออกนอกสถานที่, ลา, ไม่ระบุ
- presence รีเซ็ตเป็น "ไม่ระบุ" อัตโนมัติเมื่อสิ้นวัน เพื่อไม่ให้ค้างจากเมื่อวาน
- ลำดับแสดงงานปัจจุบัน: งานที่ปัก → งาน in_progress ที่ last_updated_at ล่าสุด
  → "ยังไม่มีงานที่กำลังทำ"
- งานที่แสดงเป็นงานลับและผู้ดูไม่มีสิทธิ์ → แสดง "งานภายใน"
- งานที่ปักถูกปิดหรือยกเลิก → ปลดหมุดอัตโนมัติ

US-21 GM แจ้งว่ากำลังทำอะไรและอยู่ที่ไหน — P1, P3, KR2.2
| Given | When | Then |
|---|---|---|
| GM เปิดงาน in_progress | แตะ "กำลังทำตอนนี้" | ปักงานนี้แทนงานเดิม หน้าแรกอัปเดตแบบสด ไม่นับเป็นความคืบหน้าสำหรับ stale |
| GM ตั้งสถานะ "อยู่ FAC16" | พนักงานเปิดหน้าแรก | เห็นสถานะพร้อมเวลาที่ตั้ง |
| ข้ามวัน | ระบบรีเซ็ต | presence กลับเป็น "ไม่ระบุ" งานที่ปักยังอยู่ |

## C8. SLA แบบ snapshot (แทน §6.1 ข้อ 6, ปรับ §6.6, US-13; อยู่ด่าน B)
- ไม่ทำระบบ version ของ policy/calendar
- เมื่อเริ่มใช้เกณฑ์กับงาน เก็บ sla_snapshot ในตัวงาน: policy_key,
  milestone_type (coordinate | resolve), duration, unit (business_days | continuous_24h),
  calendar_ref, started_at, original_due_at
- การแก้ policy หรือปฏิทินมีผลกับงานใหม่เท่านั้น งานเดิมใช้ snapshot ของตัวเอง
- ปรับเป้ารายงาน: original_due_at คงเดิมเพื่อรายงาน เป้าใหม่เก็บเป็น planned_due_at + เหตุผล
- ด่าน B เริ่ม SLA 2 แบบ: ไฟดับ/อินเทอร์เน็ตล่ม (coordinate ภายใน 1 วันทำการ)
  และค่าเริ่มต้นของแจ้งซ่อมทั่วไป (Admin ตั้งค่า) ประเภทอื่นแสดง "ยังไม่กำหนด SLA"
- การคำนวณเวลาทั้งหมด (วันทำการ, SLA, stale, auto-close, เวลารอ) อยู่ใน pure function ชุดเดียว
  สร้างตั้งแต่ด่าน A (stale/auto-close ต้องใช้) มี unit test ครอบตัวอย่าง §6.1-6.2
  และกรณีวันหยุด / สลับ waiting หลายรอบ
- US-13 แถว 4: "งานเก่าเก็บ policy/calendar เดิม" → "งานเก่าใช้ sla_snapshot ของตัวเอง"
