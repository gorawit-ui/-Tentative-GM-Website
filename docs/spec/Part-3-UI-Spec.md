## 0. หลักร่วมที่ต้องใช้ทุกหน้า

### 0.1 ขนาดหน้าจอและโครงร่าง

| ขนาด | โครงหน้า |
|---|---|
| Mobile ต่ำกว่า 768px | หนึ่งคอลัมน์, padding 16px, bottom navigation, action sheet เต็มความกว้าง; ไม่มีการเลื่อนแนวนอนในฟอร์ม |
| Tablet 768–1023px | ใช้ navigation และบอร์ดรายการแบบ mobile; ฟอร์มจำกัดความกว้างอ่านง่าย การ์ดบางพื้นที่จัดสองคอลัมน์ได้ |
| Desktop ตั้งแต่ 1024px | sidebar ประมาณ 232px, top bar, พื้นที่เนื้อหา; บอร์ด Kanban ใช้ความกว้างที่มีและเลื่อนเฉพาะพื้นที่บอร์ดเมื่อจำเป็น |

- หน้าฟอร์มบน desktop กว้างประมาณ 720px; หน้ารายละเอียดใช้ข้อมูลหลักกับแถบข้าง; Dashboard ใช้ grid โดยไม่ยืดข้อความยาวเต็มจอ
- ฟอนต์ IBM Plex Sans Thai Looped; body และช่องกรอกอย่างน้อย 16px; เป้าสัมผัสอย่างน้อย 44px และใช้ 48px เป็นขนาดปุ่มทั่วไป
- พื้นหลังครีม การ์ดขาว ปุ่มหลักสีมัทฉะ ตาม brief เดิม ใช้ข้อความ/ไอคอนคู่กับสีเสมอ
- สีเขียวในป้ายสถานะสงวนให้ completed; “ฝ่ายที่รอตอบกลับแล้ว” ใช้ป้ายข้อมูลโทนกลาง ไม่แสดงเหมือนงานเสร็จ
- stale ใช้ไอคอนนาฬิกา เส้นขอบ และคำอธิบาย ไม่ลด opacity ทั้งการ์ดจนข้อความอ่านยาก
- วันที่แสดงภาษาไทย ปี พ.ศ. เวลา Asia/Bangkok และมีเวลาชัดในเหตุการณ์สำคัญ ข้อมูลที่ยังโหลดไม่เสร็จไม่แสดงเป็น 0

### 0.2 Bottom navigation และทางเริ่มแจ้งซ่อม

เรียงซ้ายไปขวา: หน้าแรก / คำขอของฉัน / แจ้งซ่อม / บอร์ด / ติดต่อ GM

- “แจ้งซ่อม” เป็นปุ่มกลางเด่น มีทั้งไอคอนและข้อความ แตะเดียวเข้าแบบฟอร์ม maintenance ไม่ผ่านเมนูเลือกประเภท
- คง navigation นี้ในทุกหน้าหลัง login ที่ผู้ใช้มีสิทธิ์สร้าง รวมรายละเอียด Dashboard Admin และฟอร์ม หน้า QR/login ใช้ทางเข้าสู่ระบบและติดต่อ GM
- เมื่ออยู่ในฟอร์มแจ้งซ่อมแล้ว ปุ่มกลางกลับไปฟอร์ม/ร่างเดิม ไม่สร้างฟอร์มซ้ำ; หากมีฟอร์มประเภทอื่นยังไม่ส่ง ให้พักร่างของฟอร์มนั้นแล้วเปิดแจ้งซ่อม ไม่ต้องผ่าน dialog ทิ้งข้อมูล
- ร่างพักเฉพาะ session บนอุปกรณ์ ไม่ใช่รายการงานที่ส่งแล้ว ไม่เพิ่มระบบร่างข้ามอุปกรณ์/ส่งอัตโนมัติภายหลังออกนอกเครือข่าย
- action bar ประจำหน้าวางเหนือ bottom navigation และ safe area ไม่ทับช่องกรอกหรือข้อความผิดพลาด รองรับการเปลี่ยนความสูงเมื่อคีย์บอร์ดเปิด
- Viewer ที่ไม่มีสิทธิ์สร้างตาม Part 2 ใช้เมนูอ่าน 4 รายการ ไม่มีปุ่มสร้างที่กดแล้วถูกปฏิเสธ บทบาทนี้ยังใช้สิทธิ์ผู้ขอ/ผู้เกี่ยวข้องรายงานได้ตามที่ยืนยัน
- Desktop มีปุ่ม “แจ้งซ่อม” ใน top bar เสมอ; GM มี “สร้างงาน GM / เปิดแทน” แยกชัด ไม่ใช้ปุ่มกลางเปิดเมนูหลายทาง

ข้อแลกเปลี่ยน: พื้นที่แนวตั้งลดลงจาก navigation ถาวร แต่พนักงานเริ่มแจ้งซ่อมได้จากทุกหน้าด้วยตำแหน่งเดิม

### 0.3 สิทธิ์และสถานะบันทึก

- หน้ารายละเอียดเดียวมีมุมมอง summary-only และมุมมอง full-detail ตามสิทธิ์ ไม่ดาวน์โหลดข้อมูลลับมาเพียงซ่อน component
- ทุก mutation มี submitting/สำเร็จ/ล้มเหลวแยกชัด ปิดการส่งซ้ำขณะรอผล แต่ไม่ทำให้ทั้งแอปค้าง
- ไม่ประกาศว่าสำเร็จก่อน server ยืนยัน เมื่อคำสั่งชนกับการเปลี่ยนของคนอื่นให้แสดงข้อมูลล่าสุดและคงข้อความที่ผู้ใช้พิมพ์ไว้
- การอ่าน, pin, presence, waiting_party_responded และงานส่งข้อความไม่อัปเดต last_updated_at เพื่อทำให้ stale หาย
- source = trello ไม่มีปุ่มแก้งาน ย้ายสถานะ ติดตาม หรือคอมเมนต์ที่แก้ต้นทางจากเว็บ ใช้ปุ่ม “เปิดใน Trello”

## 2. UI-01 — Login / QR / ไม่มีบัญชี

### Layout
Mobile: ชื่อบริการ → คำอธิบายสั้น → ปุ่ม “เข้าสู่ระบบด้วย Google” → “ใช้บัญชี @tdfb.co” → กล่องติดต่อกรณีไม่มีบัญชี

Desktop: กล่อง login กลางหน้า กว้างประมาณ 440px ใช้ข้อความและลำดับเดียวกับ mobile ไม่ใส่ภาพตกแต่งที่เบียดปุ่มหลัก

- กล่อง “ไม่มีบัญชีบริษัท? แจ้งทีม GM” แสดงช่องทางที่ Admin อนุญาตเผยก่อน login เช่น “โทรหา GM” พร้อมชื่อผู้ติดต่อ ต้องมีช่องทางที่ไม่บังคับ Slack/company login
- เปิดจาก QR ให้จำบริบทไว้และกลับเข้า UI-03 หลัง login หากมี session อยู่แล้วข้าม login
- คนไม่มีบัญชีได้รับคำแนะนำ “ทีม GM จะช่วยเปิดเรื่องให้” ไม่พบฟอร์มส่งงานแบบไม่ระบุตัวตน
- บัญชีโดเมนอื่น/ถูกปิดใช้งานเห็นเหตุและปุ่ม “เปลี่ยนบัญชี” ไม่เห็นข้อมูลในบอร์ด

| State | การแสดงและทางไปต่อ |
|---|---|
| Empty / ไม่พบ QR | “QR นี้ใช้ไม่ได้แล้ว เลือกสถานที่เองได้” พร้อมเข้าแจ้งซ่อมหลัง login; ช่องติดต่อยังอยู่ |
| Loading | กำลังตรวจบัญชี/QR; คงกล่องติดต่อให้ใช้ได้ ไม่แสดงคำขอตัวอย่าง |
| Error | ยกเลิก login/เข้าสู่ระบบไม่สำเร็จ/ไม่มีสิทธิ์แยกข้อความกัน มีปุ่มลองใหม่หรือเปลี่ยนบัญชี |

## 3. UI-02 — หน้าแรก

### ลำดับ Mobile
1. ชื่อบริการและผู้ใช้ปัจจุบัน
2. แถบ “มี X งานรอคุณยืนยัน” เมื่อ X > 0; แตะเปิด UI-06 กรองรอยืนยัน
3. ปุ่มลัดบริการที่เปิดแล้ว: แจ้งซ่อม / คำขอของฉัน / ถามทีม GM; GM มีปุ่มสร้างงาน GM/เปิดแทน
4. “ทีม GM กำลังทำอะไร” การ์ด Napat, Gorawit, Sirirat เรียงแนวตั้ง อ่านครบโดยไม่ต้องปัดหา
5. บอร์ดย่อ: จำนวน 5 สถานะและการ์ดล่าสุดในขอบเขตที่ดูได้ พร้อม “ดูบอร์ดทั้งหมด”
6. ใน B เพิ่มช่องค้นหาเหนือบริการ, ปุ่มขอ/ส่งเอกสาร และประกาศใต้ข้อมูลบริการ

### Desktop
- แถบรอยืนยันเต็มความกว้างเหนือเนื้อหา
- ปุ่มลัดเป็นแถว; การ์ดทีม 3 ใบเรียงแถวเดียว
- บอร์ดย่อใช้พื้นที่หลัก; ประกาศใน B เป็นแถบข้างหรือแถวถัดไปเมื่อพื้นที่ไม่พอ

### TeamFocusCard
- รูปจริง/ชื่อย่อเมื่อยังไม่มีรูป, ชื่อพร้อมแยก Napat และ Sirirat ให้ไม่สับสน
- presence พร้อมเวลาที่ตั้ง; “ลา ถึง [วันสิ้นสุด]” เมื่อมี leave_until_date
- request_number, summary_title และสถานะจริงของงานที่ปัก หรือ fallback in_progress ล่าสุดของคนนั้น
- ถ้าไม่มีงานใช้ “ยังไม่มีงานที่กำลังทำ”
- งานลับที่ผู้ดูไม่มีสิทธิ์ใช้ “งานภายใน” ไม่มีเลขงาน ชื่อ ลิงก์หรือ request_id ให้เปิด
- เจ้าของ profile มีปุ่มเปลี่ยน presence; “ลา” เปิดช่องวันสิ้นสุด ไม่เลือกหมายถึงลาวันนี้ตาม A3
- วันสิ้นสุดก่อนวันนี้แสดงข้อผิดพลาดในช่อง; เปลี่ยน presence ออกจากลาแล้วไม่เก็บกำหนดลารอบเก่ามารีเซ็ตค่าภายหลัง

| State | การแสดงและทางไปต่อ |
|---|---|
| Empty | ทีมไม่มีงานกำลังทำยังแสดงสมาชิกครบ; บอร์ดว่างแสดงทางแจ้งซ่อม; แถบรอยืนยันซ่อนเมื่อโหลดแล้ว X = 0 |
| Loading | skeleton แยกแถบรอยืนยัน การ์ดทีม และบอร์ดย่อ ไม่ปลอมจำนวน 0 |
| Error | พื้นที่ใดล้มเหลวแสดงลองใหม่เฉพาะพื้นที่; ปุ่มเริ่มแจ้งซ่อมและติดต่อ GM ยังใช้ได้ |

## 4. UI-03 — แจ้งซ่อม

### Layout
Mobile: ชื่อหน้า → stepper “ขั้น 1 จาก 4” → บริบทสถานที่/บริเวณที่เลือก → เนื้อหาขั้นปัจจุบัน → ปุ่มย้อนกลับ/ถัดไปเหนือ bottom navigation

Desktop: ฟอร์มกลางหน้ากว้างประมาณ 720px ใช้ 4 ขั้นเหมือน mobile และมีสรุปบริบทด้านข้างเมื่อพื้นที่พอ ไม่แตก flow ตามอุปกรณ์

| ขั้น | Components | Validation / พฤติกรรม |
|---|---|---|
| 1 สถานที่ | ปุ่มเลือก WH300, FAC16, FAC17, Office 195, Cafe 222 | ต้องเลือกสถานที่; ไม่ใช้ GPS เดา |
| 2 บริเวณ | รายการจากสถานที่ที่เลือก พร้อมเส้นทางตำแหน่ง | เปลี่ยนสถานที่แล้วต้องทบทวนบริเวณ; ถ้ายังไม่มีบริเวณใช้ไม่ระบุและให้บอกจุดในรายละเอียด |
| 3 อาการ | ปุ่มไอคอนพร้อมชื่ออาการตาม seed data | เลือกหนึ่งอาการ; “อื่นๆ” ต้องอธิบาย |
| 4 รายละเอียด/รูป | summary_title ที่เปิดเผยได้, รายละเอียด, แนบรูป, สรุปสถานที่, ปุ่มส่ง | รูปไม่บังคับ; ชื่อที่ระบบแนะนำใช้เฉพาะอาการ/สถานที่ ไม่คัดลอกข้อความส่วนตัวมาทั้งก้อน |

- QR ที่ใช้ได้เติมสองขั้นแรกและเปิดขั้นอาการ พร้อมปุ่มแก้สถานที่/บริเวณได้
- ตัวอย่าง WH300 ใช้บริเวณจริงตาม seed; สถานที่อื่นแสดงข้อมูลที่ Admin ตั้งไว้ ไม่เอาตัวอย่าง mock ไปปน production
- แนบรูปจากกล้อง/คลังรูป แสดงภาพย่อ ลบ/ลองอัปโหลดใหม่ทีละรูปได้ ชนิดและขนาดที่รองรับแสดงจากค่ากลางของระบบ
- ก่อนส่งแสดงข้อความ “ชื่อบนบอร์ดควรเป็นชื่อกลางๆ ไม่ใส่ข้อมูลส่วนบุคคล”
- เมื่อสำเร็จแสดง “รับเรื่อง GM-0427 แล้ว” พร้อมสถานะ/ผู้รับผิดชอบจริง และปุ่มดูรายละเอียด ไม่แสดงเวลาเข้าหน้างานที่ GM ยังไม่ได้ยืนยัน
- หากผู้รับผิดชอบเริ่มต้นลา แสดง “รอทีม GM รับเรื่อง” และ “ยังไม่มอบหมาย” โดยไม่เผยเหตุการลาหรือข้อมูลติดต่อส่วนตัวแก่ผู้ขอ

| State | การแสดงและทางไปต่อ |
|---|---|
| Empty | ยังไม่เลือกข้อมูลให้ข้อความช่วยเลือก; ไม่มีบริเวณใช้ fallback ไม่ปิดกั้นการแจ้ง |
| Loading | skeleton เฉพาะรายการบริเวณ; กำลังส่งล็อกส่งซ้ำและคงข้อมูลทุกช่อง |
| Error | ชี้ช่องที่ต้องแก้; ส่งไม่สำเร็จคงรูป/ข้อความ; ถ้าผลการส่งยังไม่แน่ชัดตรวจรายการเดิมก่อนให้สร้างใหม่ |

## 5. UI-04 — GM สร้างงานเอง / เปิดแทน

Mobile ใช้หน้าเต็มหนึ่งคอลัมน์ Desktop ใช้ฟอร์มหนึ่งหน้าและสรุปสิทธิ์ด้านข้าง เริ่มจากปุ่ม “สร้างงาน GM / เปิดแทน” แล้วเห็นตัวเลือกสองแบบอยู่บนฟอร์ม

### GM สร้างงานเอง
- type = gm_task, origin = gm_initiated, ไม่มี requester_id; แสดงคำว่า “งานที่ GM เริ่มเอง”
- ฟิลด์หลักที่เห็นทันที: summary_title, category 7 หมวด, ผู้รับผิดชอบ, สถานะเริ่มต้น
- สถานที่ไม่บังคับ, related_person_ids, team_labels, ธงลับและ sensitivity_reason อยู่ในหน้าเดียว ไม่ซ่อนผู้เกี่ยวข้องไว้หลายชั้น
- เริ่มต้นผู้รับผิดชอบเป็น GM ผู้สร้างสำหรับงานที่ริเริ่มเอง แก้ได้; ไม่เอาการเลือกนี้ไปแทนผู้ขอ
- หมวดใช้ชื่อเดิม: บริหารสินค้า Damage / เอกสารและธุรการ / ทรัพย์สินและอาคารสถานที่ / จัดซื้อทั่วไปและบิล / ภาครัฐ กฎหมาย Compliance / Project ปรับปรุงระบบ / กิจกรรมพนักงาน
- เลือก waiting แล้วขยายส่วนรอและผู้รับแจ้ง inline ใช้กติกา UI-07 ไม่ต้องส่งงานก่อนแล้วเปิดไปตั้งค่าซ้ำ
- เรื่องสัญญา/บุคคลเปิดลับตามค่าเริ่มต้น การปลดธงจำกัด GM Admin พร้อมเหตุผล
- เป้าทดสอบ: กรอกงานข้ามทีมตามตัวอย่างที่มีข้อมูลพร้อมภายใน 1 นาที ไม่เพิ่มฟอร์มเฉพาะ BOI/Damage/จัดซื้อ

### GM เปิดแทน
- origin = gm_on_behalf, created_by_id = GM; เลือกประเภทบริการที่เปิดแล้ว และใช้ฟอร์มประเภทนั้น
- people picker ผู้ขออยู่บนฟอร์ม แสดงชื่อกับอีเมลเพื่อแยกชื่อซ้ำ
- “ไม่พบในรายชื่อ” เปิดช่องชื่อข้อความ พร้อม “ผู้ขอรายนี้ไม่มีบัญชีผูก งานจะปิดเมื่อ GM กดเสร็จ”
- ไม่เติม requester_id จากการเดาชื่อ และไม่ขอ email ส่วนตัวเพื่อใช้แทน @tdfb.co
- ผู้ขอที่มีบัญชีแสดงช่องทางแจ้งที่ระบบใช้ได้; ไม่ให้การจับคู่ Slack ล้มเหลวขวางการสร้าง

| State | การแสดงและทางไปต่อ |
|---|---|
| Empty | ไม่พบคนให้ลองคำค้นใหม่หรือใช้เปิดแทนแบบชื่อข้อความ; ไม่พบผู้เกี่ยวข้องไม่สร้างบัญชีเอง |
| Loading | people picker แสดงกำลังค้น; คงชื่อที่กรอกในช่องอื่น |
| Error | บอกว่าคนใดถูกปิดบัญชี/เพิ่มสิทธิ์ไม่ได้เมื่อยืนยัน; คงฟอร์มและไม่บันทึกสิทธิ์บางส่วนโดยเงียบ |

## 7. UI-06 — คำขอของฉัน

### Layout
Mobile: ชื่อหน้า → แท็บที่ฉันขอ/เกี่ยวข้องกับฉัน → quick filters รอยืนยัน/มีอัปเดตใหม่/สถานะ → การ์ดแนวตั้ง

Desktop: แท็บและ filter แถวบน รายการแบบตารางหรือการ์ดกว้าง แสดงเลขงาน ชื่อ สถานะ สถานที่ ผู้รับผิดชอบ เวลาที่อัปเดต และกำหนดยืนยันในแถวเดียวเมื่อมี

### MyRequestCard
- request_number + summary_title, ประเภท/สถานที่, สถานะ, ผู้รับผิดชอบ/ยังไม่มอบหมาย
- ขณะ waiting แสดงฝ่ายหลักและระยะเวลารอ; ถ้าฝ่ายตอบแล้วแสดงป้ายกับเวลาแทนตัวนับที่ยังเดิน
- จุดพร้อมข้อความ “มีอัปเดตใหม่” ไม่ใช้สีอย่างเดียว ใช้ last_viewed_at ของคนนี้กับงานนี้
- งาน completed ที่ตนเป็น requester แสดง “รอคุณยืนยัน” พร้อม auto_close_due_at และปุ่ม “ตรวจงาน”
- แท็บเกี่ยวข้องกับฉันไม่แสดงปุ่มยืนยันแทนผู้ขอ; ถ้าเป็นผู้รับแจ้งปัจจุบันแสดงทางเข้าไปตอบในรายละเอียด
- เปิดรายละเอียดสำเร็จจึงปรับการอ่าน ไม่เปลี่ยน stale; งานที่อ่านแล้วกลับมีจุดเมื่อมีเหตุการณ์ใหม่ที่มองเห็นได้
- งานลับที่ผู้ใช้มีสิทธิ์อ่านอยู่ในหน้านี้ได้ ไม่ทำให้ไปปรากฏบนบอร์ดสรุปทั่วไป

| State | การแสดงและทางไปต่อ |
|---|---|
| Empty | ที่ฉันขอ: “ยังไม่มีคำขอ” พร้อมแจ้งซ่อมถ้ามีสิทธิ์; เกี่ยวข้องกับฉัน: “งานที่เพิ่มคุณเป็นผู้เกี่ยวข้องจะแสดงที่นี่” |
| Loading | skeleton ตามแถว ไม่ทำให้ป้ายรอยืนยันหายแล้วกลับมาเป็นจำนวนที่ดูเหมือนเปลี่ยนจริง |
| Error | ลองใหม่และคงแท็บ/filter; ไม่มีงานตาม filter ให้ล้าง filter ไม่ใช้ข้อความเดียวกับเครือข่ายล่ม |

## 8. UI-07 — หน้ารายละเอียด Request

### Layout

| ส่วน | Mobile | Desktop |
|---|---|---|
| Header | ย้อนกลับ, request_number/คัดลอก, summary_title, สถานะ/ลับ/จาก Trello | เหมือน mobile พร้อม action ที่มีสิทธิ์ด้านขวา |
| สิ่งที่ต้องทำตอนนี้ | แถบรอยืนยัน/แผงตอบของฝ่ายที่รอ/แผง GM ตามสิทธิ์ | วางเหนือข้อมูลหลัก ไม่ซ่อนใน tab |
| ข้อมูลสรุป | สถานที่ ประเภท ผู้ขอ ผู้สร้าง ผู้รับผิดชอบ อายุงานรวม | คอลัมน์ข้างประมาณหนึ่งในสาม |
| เนื้องาน | รายละเอียด รูป และลิงก์เอกสาร | คอลัมน์หลักประมาณสองในสาม |
| รอ/ประสาน/SLA | การ์ดรอและประวัติประสาน; SLA เพิ่ม B | แถบข้างพร้อมจุดเปิด history |
| คอมเมนต์และ history | ส่วนแยกกันเรียงลง อ่านได้โดยไม่เลื่อนข้าง | คอลัมน์หลัก อ่านลำดับเหตุการณ์ได้ |
| Action | แถบ action ที่สัมพันธ์กับบทบาทเหนือ navigation | อยู่ header/แถบข้างและใกล้ส่วนงาน |

### มุมมอง summary-only
แสดงเฉพาะเลขงาน ชื่อกลาง ประเภท สถานที่ สถานะ ผู้รับผิดชอบ และรอใครที่เปิดเผยได้ พร้อม “รายละเอียดของงานนี้จำกัดเฉพาะผู้มีสิทธิ์” ไม่มีคอมเมนต์ รูป history ช่องทางแจ้ง หรือรายชื่อผู้เกี่ยวข้อง

### มุมมองตามความสัมพันธ์

| ผู้ดู | Action |
|---|---|
| requester_id ของงาน | คอมเมนต์/แนบรูป; ยืนยันหรือแจ้งยังไม่เรียบร้อยระหว่างรอยืนยัน |
| related_person_ids | อ่าน/คอมเมนต์ ไม่มีสิทธิ์เปลี่ยนสถานะหรือยืนยันแทน |
| ผู้รับแจ้งช่วงรอปัจจุบันที่มีสิทธิ์ | เพิ่มปุ่ม “ฝั่งฉันเรียบร้อยแล้ว” ตาม A2 |
| GM Staff/Admin | รับ/มอบหมาย/รอ/ติดตาม/ประสาน/เสร็จ/ยกเลิก/เปิดกลับตามกติกา |
| GM Admin | เพิ่มสิทธิ์ปลดธงลับพร้อมเหตุผล |
| source = trello | อ่านข้อมูลที่อนุญาตและเปิดใน Trello |

### ส่วนสำคัญ
- อายุงานรวมใช้เวลาจริงไม่พัก แสดงแยกจากเวลารอฝ่ายปัจจุบันและ SLA ของ GM
- งานเปิดแทนแสดงผู้ขอจริงกับ “เปิดเรื่องโดย [GM]”; ชื่อข้อความอยู่เฉพาะรายละเอียดที่จำกัดสิทธิ์
- ป้าย “ผู้ขอยังไม่ได้รับแจ้ง” อยู่ในพื้นที่ GM พร้อมสาเหตุและผลการส่งล่าสุด ไม่เผยบนมุมมองสรุป
- รอผู้อื่นก่อนตอบ: “รอ [ฝ่าย] • รอมา [เวลา]”; หลังตอบ: “ฝ่ายที่รอตอบกลับแล้ว • [เวลา]” พร้อม “รอ GM ดำเนินการต่อ”
- ใน B หลัง responded_at ให้แสดง “SLA ของ GM เดินต่อแล้ว” หาก SLA ยังไม่จบ แม้ status ยังเป็น waiting
- SLA card แสดง milestone, หน่วย, เกณฑ์รายงานตาม original_due_at, เวลาที่ใช้/เหลือหลังหักช่วงพัก และ planned_due_at แยกพร้อมเหตุผลเมื่อมี ไม่ใช้เป้าใหม่ทำให้ป้ายเกินเกณฑ์เดิมหาย
- ไม่มีเกณฑ์ใน B ใช้ “ยังไม่กำหนด SLA”; ด่าน A ไม่แสดง countdown หรือผลผ่าน SLA
- history แสดงการสร้าง รับงาน มอบหมาย ประสาน เปลี่ยนสถานะ ช่วงรอ ติดตาม waiting_party_responded การเสร็จ การยืนยัน ปิดอัตโนมัติ และเปิดกลับ พร้อมผู้ทำและเวลา โดยแยกเหตุการณ์การอ่านออกจากความคืบหน้างาน

### Action sheets ใช้ร่วมกัน

| Sheet | ข้อมูล/ปุ่ม | ผล |
|---|---|---|
| รอผู้อื่น | waiting_on.kind, คน/ทีม/ชื่อ, ผู้ติดต่อ, ตัวเลือกแจ้ง, preview สิทธิ์ | บันทึกช่วงรอและแจ้งหลังบันทึกสำเร็จ |
| เพิ่มคนในงานลับ | รายชื่อใหม่ + ยืนยันสิทธิ์แยกที่ไม่ติ๊กล่วงหน้า | ไม่ยืนยันยังบันทึกรอได้ แต่ไม่ส่งลิงก์ให้คนที่ไม่มีสิทธิ์ |
| ฝั่งฉันเรียบร้อยแล้ว | ฝ่ายที่เป็นตัวแทน, หมายเหตุไม่บังคับ, ส่งคำตอบ | waiting_party_responded/responded_at; ไม่เปลี่ยนสถานะ/stale |
| เสร็จ | สรุปผล required; ใช้ผลที่บันทึกจริงไว้ได้; แสดงว่าจะรอยืนยันหรือปิดทันที | completed และกำหนด/การปิดตาม requester_id |

| ประสานช่างแล้ว | ผู้ที่ประสานและข้อมูลขั้นต่ำ; แสดงเวลาที่จะบันทึก | history ตั้งแต่ A; ประเมิน coordinate ใน B |
| มอบหมาย | รายชื่อ GM พร้อม presence/ลา | ตั้งผู้รับผิดชอบและ history; ไม่ย้ายเพราะลาหรือกลับจากลาเอง |

### การยืนยันหลังเสร็จ

- ผู้ขอที่อยากเปิดกลับหลังปิดคอมเมนต์ติดต่อ GM ในงานเดิม; GM ใช้เปิดกลับพร้อมเหตุผล

| Empty | ยังไม่มีรูป/คอมเมนต์ใช้คำเชิญที่เกี่ยวข้อง; history งานใหม่ยังมีเหตุการณ์สร้าง |
| Loading | skeleton header/เนื้อหา; ปุ่มที่ขึ้นกับสถานะยังไม่พร้อมจนตรวจสิทธิ์เสร็จ |
| Error | บันทึกคอมเมนต์/รูปไม่สำเร็จคงข้อมูล; สิทธิ์หายให้หยุดแสดงส่วนจำกัดสิทธิ์และใช้ข้อความกลาง; รอเปลี่ยนระหว่างกดตอบให้เปิดข้อมูลล่าสุดโดยไม่บันทึกตอบช่วงเก่า |

## 9. UI-08 — บอร์ดทีม

### Mobile / Tablet: รายการแบ่งตามสถานะ
- ชื่อบอร์ด + ปุ่มสร้างงานสำหรับ GM
- แถว quick filter “ทั้งหมด / ของฉัน / ยังไม่มอบหมาย” และปุ่ม filter คน/ประเภท/สถานที่; team_labels อยู่ใน filter เพิ่มเติมเพื่อไม่เบียดพื้นที่
- ค่าเริ่มต้น GM เห็นทั้งทีม เพื่อไม่ซ่อนคิวไม่มอบหมาย; จำ filter ที่ผู้ใช้เลือกและมีล้าง filter ชัด
- รายการเป็น 5 กลุ่มแนวตั้ง รอคิว / กำลังทำ / รอผู้อื่น / เสร็จ / ยกเลิก
- รอคิว กำลังทำ รอผู้อื่นเปิดกลุ่มเป็นค่าเริ่มต้น; เสร็จ/ยกเลิกย่อได้ พร้อมจำนวนที่กดขยาย
- มีปุ่มเลือกสถานะเพื่อไปยังกลุ่มนั้น และจำนวนงานตาม filter
- ไม่มี Kanban 5 คอลัมน์ ไม่มี long-press เพื่อ drag และไม่มี horizontal scroll ของการ์ด
- มุมมองตามคน/สถานที่จัดเป็นกลุ่มรายการเดียวกัน สถานะบนการ์ดยังชัด

### Desktop: Kanban
- toolbar: มุมมองสถานะ/คน/สถานที่, filter, ยังไม่มอบหมาย, ปุ่มสร้างงาน
- มุมมองสถานะมี 5 คอลัมน์ ความกว้างการ์ดประมาณ 260–320px; เลื่อนแนวนอนเฉพาะบอร์ดได้เมื่อพื้นที่ไม่พอ
- drag handle เฉพาะ GM และงานเว็บ พร้อมปุ่ม action บนการ์ดเช่นเดียวกับ mobile
- drop เข้า waiting/completed/cancelled เปิด sheet ข้อมูลที่จำเป็น ก่อนบันทึกจริง ถ้ายกเลิก sheet คืนตำแหน่งเดิม
- ผู้ใช้ keyboard ใช้ปุ่มสถานะแทน drag ได้ ไม่มีการทำงานที่ต้องลากเท่านั้น

### RequestCard
1. request_number และไอคอนประเภท; ป้ายจาก Trello/ลับตามสิทธิ์
2. summary_title ไม่เกินสองบรรทัดในรายการ เปิดรายละเอียดอ่านเต็ม
3. สถานที่/บริเวณ และผู้รับผิดชอบหรือ “ยังไม่มอบหมาย”
4. สถานะ/ฝ่ายที่รอ; team_labels แสดงเท่าที่ไม่เบียดชื่อ
5. สัญญาณที่ต้องจัดการ: stale, ฝ่ายตอบแล้ว, ผู้ขอยังไม่ได้รับแจ้งเฉพาะ GM, รอยืนยัน; SLA เพิ่ม B
6. แถว action สำหรับ GM ตามสถานะ อยู่บนการ์ดโดยตรง

ลำดับป้ายเมื่อมีหลายเรื่อง: ข้อผิดพลาดการแจ้งที่ GM ต้องจัดการ → ฝ่ายตอบแล้ว → stale → SLA → ข้อมูลรอง; ป้ายทั้งหมดเปิดดูได้ในรายละเอียด ไม่ซ้อนทับปุ่ม

### จำนวนแตะจากการ์ดสำหรับงานที่ใช้บ่อย

นับการแตะเพื่อเรียกและยืนยัน action; การพิมพ์ผล/หมายเหตุที่จำเป็นไม่ถูกนับเป็นการเปิดเมนู UI ต้องไม่เพิ่มหน้าหรือเมนูคั่นเพื่อให้เกินสองแตะ

| Action | ทางกด | จำนวน |
|---|---|---|
| รับเรื่องที่ยังไม่มอบหมาย/เป็นของตน | รับเรื่อง | 1 |
| รับแทนคนอื่น | รับแทน → ยืนยันผู้รับผิดชอบใหม่ | 2 |
| ติดตามแล้ว | ติดตามแล้ว บันทึกทันที | 1 |
| ติดตามพร้อมเตือนซ้ำ | ปุ่มทางเลือกข้างติดตาม → ตรวจผู้รับและส่ง | 2 เมื่อผู้รับ/สิทธิ์เดิมพร้อม |
| เสร็จ | เสร็จ → sheet สรุปผล → ยืนยันเสร็จ | 2 ปุ่มดำเนินการ; ช่องผล autofocus และต้องมีเนื้อหาจริง |
| กลับกำลังทำหลังฝ่ายตอบ | กลับมาทำต่อ | 1 |
| ปักงาน in_progress | กำลังทำตอนนี้ | 1 |
| มอบหมาย | แตะชื่อผู้รับผิดชอบ → เลือก GM | 2 ในกรณีปกติ |

- รับเรื่องของตน/งานว่างมีผลเป็น in_progress และผู้รับผิดชอบถูกต้อง ไม่เรียกสิ่งนี้ว่าประสานช่างแล้ว
- “ติดตามแล้ว” เป็นปุ่มตรง ไม่เปิด modal โดยบังคับ; หมายเหตุเป็นตัวเลือกเพิ่มเติม
- ปุ่มเสร็จต้องเห็นตั้งแต่บนการ์ด in_progress ไม่ต้องเปิดรายละเอียดก่อน ช่องสรุปไม่เติมว่าแก้แล้วเอง
- รอผู้อื่น/เปลี่ยนฝ่ายใหม่เป็นงานที่ต้องเลือกข้อมูล จึงใช้ sheet เดียวพร้อมทุกช่อง ไม่อ้างว่าการกรอกฝ่ายใหม่หลายช่องเสร็จได้ในสองแตะ
- สิทธิ์งานลับ ข้อมูลที่จำเป็น และการตรวจสถานะล่าสุดยังต้องครบ ไม่ลดขั้นยืนยันสิทธิ์เพื่อให้ตัวเลขแตะต่ำ
- waiting ที่ฝ่ายตอบแล้วเน้น “กลับมาทำต่อ” มากกว่าเตือนซ้ำ ปิดเตือนซ้ำของช่วงที่ตอบแล้ว
- งานพร้อมกันจากสอง GM ให้คนที่ช้ากว่าเห็น “งานนี้มีผู้รับแล้ว” และข้อมูลปัจจุบัน ไม่อ้างว่ารับสำเร็จทั้งสองคน

| State | การแสดงและทางไปต่อ |
|---|---|
| Empty | แต่ละกลุ่มแสดง “ยังไม่มีงานในสถานะนี้”; ถ้า filter ว่างมีปุ่มล้าง filter; ยังไม่มอบหมาย 0 ไม่ใช่ error |
| Loading | skeleton การ์ดใน layout ของอุปกรณ์ ไม่สลับ mobile เป็น Kanban ชั่วคราว |
| Error | คง filter/ตำแหน่ง scroll; listener หลุดแสดงข้อมูลล่าสุดพร้อมเวลาและลองใหม่; mutation ไม่สำเร็จการ์ดไม่ย้ายเป็นผลสำเร็จปลอม |

งานลับบนมุมมองสรุปมีเพียง “งานภายใน X รายการ” ไม่แจกแจงจำนวนตามคน/สถานที่/ประเภทที่อาจใช้ไล่ย้อน มุมมอง GM ใช้ข้อมูลที่ GM มีสิทธิ์

## 12. UI-11 — Dashboard / Scorecard / CSV

เปิด B ให้ gm_staff/gm_admin/viewer ตามขอบเขตข้อมูล แสดงเวลาอัปเดตและขอบเขตสิทธิ์ตลอด

### Layout
Mobile: ชื่อ/ข้อมูล ณ → ตัวกรอง → metric cards สองคอลัมน์เมื่ออ่านตัวเลขได้ มิฉะนั้นหนึ่งคอลัมน์ → กราฟเรียงลง → รายการรอ → Scorecard → export

Desktop: filter แถวบน → metric cards 4 ใบ → กราฟสองคอลัมน์ → รายการรอและคอขวด → Scorecard 4 ใบ → export

กราฟทุกชนิดมีชื่อหน่วย ช่วงเวลา ฐานข้อมูล และทางดูค่าเป็นรายการ/table ไม่อาศัย hover อย่างเดียว

| Component | ข้อมูลและการกดต่อ |
|---|---|
| Filters | สัปดาห์นี้/เดือนนี้/ไตรมาสนี้, คน, ประเภท, สถานที่; แสดงช่วงวันที่จริงและล้างค่าได้ |
| Metric cards | งานทั้งหมด, % ทำตาม SLA, รอผู้อื่น, stale; แตะเปิดรายการที่มีสิทธิ์ใน filter เดียวกัน |
| Donut | 5 สถานะ; ตรงกลาง % completed จาก cohort งานที่สร้าง ไม่ใช้ % SLA แทน |
| Stacked bar | งานรายคนแยกสถานะ พร้อม “ยังไม่มอบหมาย” |
| Maintenance by location | แสดง WH300/FAC16/FAC17/Office 195/Cafe 222 ครบ แม้บางแห่งเป็น 0 |
| รายการรอผู้อื่น | ผู้ที่ยังไม่ตอบแสดงเวลารอเดิน; ผู้ตอบแล้วแสดงเวลารอที่หยุดและเวลา responded_at พร้อมป้ายรอ GM |
| งานเข้า vs ปิด | เหตุการณ์รายสัปดาห์ พร้อมจำนวนเปิดกลับ/ยกเลิกประกอบตาม PRD |
| รอใครบ่อยที่สุด | จำนวน Request ไม่ซ้ำต่อฝ่าย และเวลารอจริงสะสมที่ตัด ณ responded_at หรือจบช่วงเมื่อไม่มีคำตอบ |
| SLA breakdown | แสดงจำนวนประเมินได้/ยังรอผล/ไม่มี SLA แยก; ฐาน 0 ใช้ “ยังประเมินไม่ได้” |

- ตัวเลขสถานะ waiting อาจยังรวมงานที่ฝ่ายตอบแล้ว จึงมีข้อความรอง “ฝ่ายตอบแล้ว รอ GM ดำเนินการต่อ X งาน”; เวลารอคอขวดไม่เดินต่อในกลุ่มนี้
- ไม่เปลี่ยนกราฟอันดับความถี่เป็นอันดับช้าที่สุดโดยเงียบ จำนวนงานกับระยะเวลาต้องติดหน่วยต่างกัน
- Viewer/Scorecard ใช้ aggregate ตาม C11 ไม่โหลดรายละเอียดรวมเอง; งานลับมีเพียงจำนวนรวมที่อนุญาต ไม่ให้ drill-down หรือ export แถวลับ
- ตัวเลขช่วงงานสร้างกับกราฟเหตุการณ์ปิดอาจไม่เท่ากัน ใช้คำอธิบายฐานใกล้กราฟ

### Scorecard

| Tile | การแสดง |
|---|---|
| งานซ่อมค้าง | ตัวเลขอัตโนมัติจากงานเว็บ maintenance ใน queued/in_progress/waiting ณ snapshot; เป้า ≤ 2; completed รอยืนยันแสดงแยก |
| เอกสารลงทะเบียนเกิน 3 วัน | “ยังไม่เชื่อมข้อมูล”, เป้า 0, ลิงก์ “รายการรับ-ส่งเอกสาร พัสดุ ประจำวัน” |
| ทรัพย์สินไม่ลงทะเบียน | “ยังไม่เชื่อมข้อมูล”, เป้า 0, ลิงก์ “[Master] ทะเบียนทรัพย์สิน ครุภัณฑ์เครื่องจักรและอุปกรณ์” |
| ต่ออายุค้าง/สัญญารอดำเนินการ | “ยังไม่เชื่อมข้อมูล”, เป้า 0, ลิงก์ “สถานที่จัดเก็บเอกสารตัวจริง_รายการต่ออายุเอกสาร” |

ไม่มี URL ให้แสดง “ยังไม่ได้ตั้งลิงก์” ไม่มีปุ่มที่พาไป URL เดา และไม่แสดง 0 แทนสถานะยังไม่เชื่อม

Export CSV เปิด sheet เลือกสัปดาห์/ขอบเขตที่ได้รับอนุญาต แสดงเวลา snapshot แล้วดาวน์โหลด; ไทยอ่านได้ ช่องตัวเลขของข้อมูลไม่เชื่อมว่างและมีสถานะกำกับ ไม่เปลี่ยน export เป็นช่องทางเปิดข้อมูลที่ UI ปิดไว้

| State | การแสดงและทางไปต่อ |
|---|---|
| Empty | กราฟไม่มีข้อมูลแสดงคำอธิบาย/ล้าง filter; SLA ฐาน 0 แสดงยังประเมินไม่ได้; ไม่เชื่อมแยกจาก 0 จริง |
| Loading | skeleton metrics/charts; ขณะเปลี่ยน filter ระบุว่ากำลังอัปเดต ไม่ติดป้ายช่วงใหม่กับค่าเก่า |
| Error | retry ราย widget หรือ export; แสดงข้อมูลล่าสุดพร้อมเวลาได้แต่ต้องบอกว่าไม่ล่าสุด ไม่ใช้ค่าศูนย์แทนความผิดพลาด |

## 13. UI-12 — Admin

gm_admin เท่านั้น Mobile ใช้รายการหัวข้อ → หน้าแก้ไขเต็ม Desktop ใช้เมนูย่อยด้านซ้าย → ตาราง/ฟอร์มด้านขวา ทุกฟอร์มแสดงผลบันทึกและคงค่าหากผิดพลาด

### 13.1 สถานที่และบริเวณ — A
- รายการ 5 สถานที่พร้อมจำนวนบริเวณ/สถานะ → เลือกสถานที่ → เพิ่ม/แก้ชื่อ/ปิดบริเวณ

- ปิดบริเวณที่มีงานเก่าได้โดยงานเก่ายังคงอ่านตำแหน่งเดิม ไม่ลบอ้างอิงเก่า

### 13.2 QR — A
- เลือกสถานที่/บริเวณ → preview QR พร้อมชื่อที่อ่านได้ → เปิดลิงก์ทดสอบ → ดาวน์โหลด/พิมพ์
- มีสถานะใช้งาน/ปิดใช้งาน; QR ปิดแล้วให้ผู้ใช้เลือกสถานที่ใหม่ได้
- หน้า preview ไม่ถือว่าเกิด Request และไม่ออก request_number จนผู้ใช้ส่งงานจริง

### 13.3 ผู้ใช้ / role / ผู้รับผิดชอบเริ่มต้น — A
- people list ค้นชื่อ/อีเมล แสดง role, สถานะบัญชี, Slack จับคู่แล้ว/ยังไม่จับคู่ และ email fallback ที่ใช้ได้
- แก้ role แยกจากการเพิ่ม related person ของงาน ไม่มีระบบสมาชิกทีมทั้งบริษัท
- ส่วน “ผู้รับผิดชอบเริ่มต้น” ตั้งตามประเภทงานได้ตาม Part 1 เช่น maintenance = Sirirat; แสดงคำอธิบายว่าหากลา งานใหม่จะยังไม่มอบหมาย
- วิธีนำเข้าจาก Directory/ไฟล์ตัดสินใน Part 6 UI แสดงผลนำเข้า/รายการที่ต้องแก้ตามช่องทางที่เลือก ไม่สมมติว่าเชื่อม Directory แล้ว
- ปุ่มแก้สิทธิ์ต้องยืนยันผู้ใช้เป้าหมายและ role ใหม่ ไม่เปิด self-escalation

### 13.4 ปฏิทิน — A/B
- A มีเฉพาะปฏิทินบริษัท จันทร์–ศุกร์ พร้อมเพิ่ม/แก้วันหยุด และข้อความตรวจวันหยุด ธ.ค. 2026–ม.ค. 2027 ก่อน pilot
- B เพิ่มตัวเลือกบริษัท/รายสถานที่ และวันเปิดทำการ รวมเสาร์–อาทิตย์ได้
- Mobile ใช้รายการวันและวันหยุดตามเดือน Desktop ใช้ month view คู่กับรายการวันหยุด ไม่บังคับลากในปฏิทิน
- แสดงคำอธิบาย 1 วันทำการ = สะสม 24 ชั่วโมงบนวันที่เปิดทำการ; ไม่มีระบบเวลาทำงานรายชั่วโมง/กะ
- การแก้ค่าไม่เปลี่ยน sla_snapshot ของงานเดิม ไม่เพิ่มหน้า history/version ของ policy/calendar

### 13.5 เนื้อหาและลิงก์ — A/B
- A: ข้อมูลติดต่อ/หน้าที่/FAQ, ช่องทางช่วยเหลือก่อน login ที่ระบุว่าเปิดเผยได้, ลิงก์บริการเดิม
- B: ประกาศบนหน้าแรก และลิงก์ชีทต้นทาง Scorecard

- ช่องทางช่วยเหลือก่อน login แยกจากข้อมูลที่แสดงเฉพาะหลัง login อย่างชัดเจน

### 13.6 SLA / digest — B
- SLA แสดงสองแม่แบบ: ไฟดับ/อินเทอร์เน็ตล่ม milestone_type = coordinate ระยะเวลา 1 business_days; แจ้งซ่อมทั่วไปให้ Admin ตั้งค่าเริ่มต้น
- ช่องแก้ค่าทั่วไปมี milestone, duration, unit, calendar ที่ใช้; เปลี่ยนแม่แบบใช้กับงานใหม่ งานเก่าใช้ snapshot
- ประเภทอื่นแสดงยังไม่กำหนด SLA ไม่สร้างฟอร์ม policy จำนวนมากใน Phase 1

- digest ตั้งเวลาตาม PRD และแสดง timezone; ค่าเริ่มต้น 09:00 Asia/Bangkok เฉพาะวันที่มีสถานที่รับผิดชอบเปิดทำการ

## 15. UI-14 — PWA และเครือข่าย

- B เพิ่มเมนู “ติดตั้งบนอุปกรณ์” เมื่ออุปกรณ์รองรับ; ถ้าไม่มี prompt ให้คำแนะนำที่ตรงความสามารถของอุปกรณ์ ไม่เปิดปุ่มที่ทำอะไรไม่ได้

|---|---|
| Empty | ติดตั้งแล้วซ่อนปุ่มติดตั้ง; อุปกรณ์ไม่รองรับยังใช้เว็บได้ |
| Loading | กำลังตรวจ/เชื่อมต่อโดยไม่แสดง success ก่อนจริง |
| Error | ติดตั้งไม่สำเร็จกลับใช้เว็บได้; offline ไม่ทิ้งฟอร์มและไม่ queue mutation แบบเงียบ |

## 17. Components ร่วม, motion และ accessibility

### Components ที่ต้องนำกลับมาใช้
AppShell / BottomNav / DesktopSidebar / RequestCard / StatusChip / WaitingBadge / UnreadMarker / DeliveryBadge / PersonPicker / TeamLabelInput / RequesterPicker / ActionSheet / PresenceSheet / PhotoUploader / HistoryList / FilterBar / EmptyState / Skeleton / InlineError / Toast

### Motion
- การ์ดที่เปลี่ยนกลุ่ม/คอลัมน์เคลื่อนตามผลที่ยืนยันแล้ว ไม่แสดงว่าย้ายสำเร็จก่อนตรวจข้อมูล

- ป้ายเปลี่ยนแบบ crossfade, page transition เบา, ตัวเลข/กราฟอัปเดตเฉพาะครั้งที่ข้อมูลเปลี่ยน ไม่วนตกแต่ง
- การโหลดใช้ skeleton; prefers-reduced-motion ใช้ skeleton นิ่งและปิดการเคลื่อนไหว/count-up/การลากแบบ spring
- รายละเอียด duration/easing และ contrast ทุกคู่สีตรวจใน Part 4 เอกสารนี้ไม่อ้างว่าผ่านการวัดแล้ว

## 18. เกณฑ์รับ UI ก่อนส่งต่อ build

### ด่าน A
1. ผู้ใช้ที่มีสิทธิ์เริ่มแจ้งซ่อมได้จากปุ่มกลางหนึ่งแตะทุกหน้าหลัง login; ข้อมูลที่กรอกค้างไม่หายเมื่อพักร่างใน session
2. GM mobile ใช้รายการแบ่งสถานะ; รับเรื่อง/ติดตามแล้ว 1 แตะ และเสร็จไม่เกิน 2 ปุ่มดำเนินการจากการ์ด โดยยังต้องมีผลจริง
3. gm_task ข้ามทีมสร้างได้ในหนึ่งหน้า ภายในหนึ่งนาทีเมื่อเตรียมข้อมูลแล้ว
4. แถบรอยืนยันและ unread ใช้ความสัมพันธ์ของผู้ใช้ ไม่ล้าง stale หรือเปิดเผยงานที่ไม่มีสิทธิ์
5. ไม่มี Slack mapping ใช้ company email; ไม่มีบัญชีเห็นช่องทางติดต่อจริงใน QR/login และใช้เปิดแทนแบบชื่อข้อความ
6. ฝ่ายรอปัจจุบันตอบได้เฉพาะงานที่มีสิทธิ์; ผู้รับเก่าหรือ related person ทั่วไปตอบแทนไม่ได้
7. คำตอบไม่เปลี่ยน status/last_updated_at; ตอบซ้ำหรือคนในทีมตอบพร้อมกันเกิดผลครั้งเดียว
8. ลาพร้อมวันสิ้นสุดคงอยู่ถึงสิ้นวันนั้น งานใหม่เข้าคิวไม่มอบหมายและแจ้ง GM ทุกคน; งานเก่าไม่ย้ายเอง
9. request_number ปรากฏทุกจุดที่ได้รับอนุญาต; งานลับไม่รั่วเลข/ชื่อบนบอร์ดสรุปหรือข้อความแจ้ง
10. ทุกหน้า/ส่วนมี empty/loading/error ตามตาราง; เครือข่ายหรือ Slack/email ล้มเหลวไม่แสดงความสำเร็จปลอม
11. ประสานช่างมี history ตั้งแต่ A, auto-close ใช้ 3 วันทำการและปฏิทินบริษัทที่มีวันหยุดจริง

### ด่าน B
1. งานที่ฝ่ายตอบแล้วแต่ยัง waiting แสดงเวลารอที่หยุดและ SLA GM ที่กลับมาเดินตาม snapshot
2. Dashboard/Scorecard/CSV ใช้ฐานและสิทธิ์เดียวกัน; ตัวไม่เชื่อมแสดงสถานะ ไม่ใส่ศูนย์แทน
3. Search จำกัดเลขงาน/summary_title; Slack action ตรวจสิทธิ์ล่าสุดเหมือนเว็บ
4. เอกสารอย่างง่าย ประกาศ PWA และปฏิทินรายสถานที่อยู่ B โดยไม่เป็น dependency ของ A
5. Trello เป็น milestone ท้ายและไม่ขวาง release

## 19. การตัดสินใจที่ใช้ใน UI และงานต่อ

| การตัดสินใจ | เหตุผล/ข้อแลกเปลี่ยน |
|---|---|
| Mobile รายการ, desktop Kanban | มือถือแตะ action ได้แม่นและอ่านชื่อครบ; desktop เห็นหลายสถานะพร้อมกัน |
| ปุ่มเสร็จใช้ sheet เดียว | รักษาสรุปผลที่ตรวจสอบได้และให้เส้นทางสั้น ไม่เติมผลแทน GM |
| ผู้ติดต่อทีมตอบคนแรกจบรอบวัดเวลา | ตรงกับฝ่ายหลักหนึ่งฝ่ายต่อช่วง; หากยังมีงานเพิ่มต้องเปิดช่วงรอใหม่ชัดเจน |
| ข้อมูลอ่านใหม่แยกจาก stale | ผู้ขอหรือฝ่ายรอตอบแล้วไม่ทำให้การไม่อัปเดตของ GM ถูกซ่อน |
| ลาแล้วคิวใหม่ไม่มอบหมาย | ทำให้ทีมเห็นงานที่ต้องรับแทน โดยไม่เพิ่มการจัดเวรอัตโนมัติ |
| ร่างใน session เท่านั้น | รักษาทางแจ้งซ่อมหนึ่งแตะและไม่เพิ่มระบบ offline sync/ร่างข้ามอุปกรณ์ |
| หน้าก่อน login เปิดเฉพาะช่องทางติดต่อ | คนไม่มีบัญชียังแจ้งได้ โดยไม่เปิดข้อมูลบอร์ดหรือรายชื่อบริษัท |
