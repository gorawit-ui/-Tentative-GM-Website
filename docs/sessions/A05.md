## ส่วนที่ 2 — A05

### FU-27 (ตัดสินตามผู้ใช้)

stale คำนวณจาก**ปฏิทินบริษัทปัจจุบัน** (`calendars/company`) ไม่ใช่ snapshot ที่เก็บกับงาน — วันหยุดพิเศษที่ประกาศหลังสร้างงานต้องนับ; SLA ด่าน B ยังใช้ snapshot ตาม C8 และการเก็บ `work_calendar_snapshot` ตอนสร้างงานยังอยู่ใน [FU-27](../FOLLOW-UPS.md) สำหรับด่าน B

### stale (Part 6 §6.9, S03, U4, D-S05-3)

- `@gm/time` ใหม่ `staleDueAt(last_updated_at, calendar)` = `addBusinessDuration(…, 3 BD + 1 ms)` — 1 ms เป็นเวลาทำการ ไม่ใช่ wall clock (ขอบวันหยุดไปตกวันเปิดถัดไป)
- **เก็บเวลาที่งานจะ stale ไว้ล่วงหน้า**: ทุกครั้งที่เขียนงาน (สร้าง + pipeline ร่วมของทุกคำสั่ง) เขียน `scheduled_work/stale-{id}` (`kind: stale`, `next_run_at` = `staleDueAt`, `expected_revision`); งานที่ไม่เปิด (`completed`/`cancelled`/ปิด) → `superseded` — tick อ่านเฉพาะ job ที่ถึงเวลา ไม่อ่านงานเปิดทุกงาน
- job ของ worker: ตรวจ status / revision / เวลาจริงบนงานล่าสุด; เกิน 3 วันทำการจริง → `gm_request_summaries.stale = true` (เฉพาะข้อมูล GM, U4); ยังไม่ถึง (เช่น มีวันหยุดเพิ่ม) → รันใหม่ที่เวลาใหม่; ไม่แตะ `last_updated_at` / revision / `activity_seq`; ค่าเท่าเดิมไม่เขียน
- กฎ D-S05-3: คำสั่ง GM (รับเรื่อง/เข้ารอ/ติดตามแล้ว ฯลฯ) เริ่มนับใหม่; การตอบของฝ่ายที่ถูกรอเลื่อนแค่ revision เวลาที่จะ stale เท่าเดิม; `waiting` ยัง stale ได้; ครบ 3 วันทำการพอดียังไม่ stale
- **Admin เพิ่ม/แก้วันหยุด**: transaction ที่ tick ใช้จับ lease อ่าน `calendars/company` แล้วเทียบ hash ของเนื้อหากับค่าที่เก็บใน `scheduled_work/tick` — เปลี่ยน → สร้าง job `stale` แบบ `scope: calendar` 1 ตัว ซึ่งไล่งานที่เปิดอยู่ (หน้าละ 50, สูงสุด 4 หน้าต่อรอบ, ที่เหลือรอบถัดไป) คำนวณ `stale`/`stale_threshold_at` ใหม่ (รวมการเอาป้ายออกเมื่อวันหยุดที่เพิ่มทำให้ยังไม่ครบ) และเลื่อน job ของแต่ละงาน — เขียนเฉพาะงานที่ค่าเปลี่ยน; tick ปกติอ่านเพิ่ม 2 เอกสาร (ปฏิทิน + job รีเซ็ตสถานะที่อยู่)
- สรุปสาธารณะมีแค่ `last_updated_at` สำหรับข้อความกลาง “อัปเดตล่าสุด X วันทำการที่แล้ว” ไม่มี `stale` / `stale_threshold_at`; `requests/{id}` ก็ไม่มี

### รีเซ็ตสถานะที่อยู่ (C7, S07)

- job `scheduled_work/presence_reset` วันละครั้งที่เที่ยงคืนเวลากรุงเทพ (tick สร้างให้ถ้ายังไม่มี) อ่านรายชื่อ GM จาก `settings/routing` และ `gm_profiles` ของแต่ละคน ใช้ `resetPresence` ของ S07 บน profile ล่าสุด: ค่าที่หมดอายุ → `ไม่ระบุ` (ลบ `presence_updated_at`, `leave_ends_on`) คงหมุดงาน; ลาที่มีวันสิ้นสุดอยู่ถึงสิ้นวันนั้น; tick ที่มาช้าไม่ล้างค่าที่ GM ตั้งของวันใหม่; แล้วตั้งเวลารอบถัดไปเป็นเที่ยงคืนถัดไป
- tick ซ้อนกัน: lease ของ A02 ทำให้ทำงานครั้งเดียว และ job แต่ละตัวมี lease ของตัวเอง

## คำถามค้าง (ไม่เดา — ทำตามข้อที่ระบุไว้ก่อน รอยืนยัน)

1. **Q-A05-1 ผู้เกี่ยวข้องที่ใส่ตอนสร้างงาน** — D-A04-3 ทำกับคำสั่ง `add_related_persons`; ผู้เกี่ยวข้องที่ GM ใส่ตอนสร้างงาน (`create_gm_task` / `create_on_behalf`) ยังไม่ได้ DM (ตามเดิม) แม้เหตุผลเดียวกันจะใช้ได้ — ควรส่งด้วยหรือไม่
2. **Q-A05-2 related เดิมที่เพิ่งได้ grant งานลับ** — คนที่เป็น related อยู่แล้วแต่ไม่มี grant แล้ว GM ยืนยันให้สิทธิ์ผ่าน `add_related_persons` ไม่ได้ DM (ไม่ใช่ “ถูกเพิ่มเป็นผู้เกี่ยวข้อง”) — ยืนยัน
3. **Q-A05-3 ปฏิทินเปลี่ยนมีผลภายใน ≤ 15 นาที** — tick ตรวจ hash แล้วคำนวณใหม่ในรอบถัดไป; หน้าจอแก้ปฏิทินของ A11 อาจสร้าง job ใน transaction เดียวกันเพื่อให้มีผลทันที ([FU-32](../FOLLOW-UPS.md)) — พอหรือไม่
4. **Q-A05-4 tick แรกที่ยังไม่มี hash** — คำนวณงานที่เปิดอยู่ใหม่ 1 รอบ (ปลอดภัยไว้ก่อน เช่นตอน deploy ครั้งแรก) — ยืนยัน
5. **Q-A05-5 job รีเซ็ตสถานะที่อยู่ล้มเหลวครบ 5 ครั้ง** — คงสถานะ `failed` ให้ Admin เห็น (FU-25) และ tick ไม่สร้างใหม่เอง (หน้าแรกยังแสดงค่าที่หมดอายุเป็น “ไม่ระบุ” จาก `effectivePresence`) — ให้ tick สร้างใหม่วันถัดไปหรือไม่
