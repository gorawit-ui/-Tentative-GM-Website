## ส่วนที่ 2 — A06

### จุด “มีอัปเดตใหม่” (D-A03-5, Part 2 Addendum A1.1, U1)

- ตัวงาน: `activity_seq` เริ่มที่ 1 ตอนสร้าง (+1 ทุกเหตุการณ์ lifecycle), `last_activity_at`
- `user_state/{คน}/requests/{id}`: `activity_seq` = ลำดับล่าสุดที่คนนั้นมีสิทธิ์เห็น, `last_seen_activity_seq` = ลำดับที่เปิดดูแล้ว → จุด = `activity_seq > last_seen_activity_seq`
- สร้างงาน: ผู้สร้างเห็นแล้ว (ไม่มีจุด); GM เปิดแทน → ผู้ขอมีจุด; related ที่ GM ใส่ตอนสร้างมีจุด
- เหตุการณ์ lifecycle: ผู้ขอ + related ที่อ่านได้ ได้ลำดับใหม่ทุกครั้ง; **watcher เฉพาะเมื่อ `status` เปลี่ยน** (ยืนยันปิด/ปิดอัตโนมัติไม่ขึ้นจุดให้ watcher); **ผู้ทำ action ถูกบันทึกว่าเห็นแล้ว** (ทำบน revision ล่าสุดจึงเห็นทุกอย่างถึงตรงนั้น — Q-A06-3)
- `GET /api/me/requests`: การ์ดมี `has_update` และ `activity_seq`
- **`POST /api/requests/:id/seen` `{ activity_seq }`** (ใหม่): หน้าจอแจ้งลำดับที่แสดงสำเร็จ → `last_seen = max(เดิม, min(ที่แสดง, ที่เห็นได้))` จึงไม่ล้างจุดของเหตุการณ์ที่เข้ามาระหว่างอ่าน; ต้องเป็นเจ้าของ `user_state` ที่ความสัมพันธ์ยังจริง (ผู้ขอ/related ที่อ่านได้/watcher ของงานไม่ลับ) ไม่งั้น 404; body อื่น/ค่าติดลบ → 400 — เพิ่มใน API matrix และ [ACL-MATRIX](../spec/ACL-MATRIX.md)

### “มี X งานรอคุณยืนยัน” (D-S10-2)

endpoint เดิม `GET /api/me/awaiting-confirmation` (งานที่ฉันเป็นผู้ขอ `completed` และยังไม่ปิด) — test ยืนยันว่าเพิ่มเมื่อ GM กดเสร็จ ลดทันทีหลังยืนยันหรือ “ยังไม่เรียบร้อย” และ watcher เป็น 0 เสมอ

### ป้าย “ผู้ขอยังไม่ได้รับแจ้ง” (A1.2/A1.3, UI-15, FU-23 ส่วน badge)

- กติกา pure ใน `packages/domain/src/requester-notice.ts` (`requesterNoticeAfter`): ส่งไม่สำเร็จ (`failed` → `NO_CHANNEL` หรือ `DELIVERY_FAILED` + code) / `delivery_unknown` → ขึ้นป้ายพร้อมลำดับของเหตุการณ์ เว้นแต่ผู้ขอรู้ลำดับที่ใหม่กว่าแล้ว; ประกาศถึงผู้ขอที่ลำดับเดียวกันหรือใหม่กว่าส่งถึง หรือผู้ขอเปิดดูอัปเดตนั้นในเว็บ → ป้ายหาย; GM กดเสร็จไม่ล้างป้าย; ผู้ขอแบบชื่อข้อความ → `NO_ACCOUNT` ตั้งแต่สร้าง ไม่หายเอง
- เก็บใน `gm_request_details/{id}` (`requester_not_notified`, `requester_notified_seq` — GM only, D-S09-5) และคัด `requester_not_notified` ลง `gm_request_summaries/{id}`; **ไม่อยู่ใน `requests/{id}` และ `request_summaries`**; คำสั่ง lifecycle rebuild summary แล้วป้ายยังอยู่
- ผู้เขียน: ตอนสร้าง (`NO_ACCOUNT`), worker ตอนผลส่งถึงผู้ขอ settle (รวม `NO_CHANNEL` ตอน claim และ `LEASE_EXPIRED`) ใน transaction เดียวกับ outbox, และ endpoint `seen` ของผู้ขอ — เขียนเฉพาะเมื่อค่าเปลี่ยน

### FU-08 (ปิด)

## คำถามค้าง (ไม่เดา)

1. **Q-A06-1 ประกาศสร้างงานกับ D-A03-7** — ตอนนี้ระงับเฉพาะประกาศสถานะ (รับเรื่อง/เสร็จ/ยังไม่เรียบร้อย/ยกเลิก/เปิดกลับ/รับต่อ) ประกาศ “GM เปิดงานแทนคุณ” (`request_created` ถึงผู้ขอ, D-A01-4) ไม่ถูกระงับแม้จะมีประกาศสถานะตามมา → ผู้ขอแบบเปิดแทนอาจได้ 2 ข้อความ (สร้าง + ล่าสุด) — ให้ประกาศสร้างงานถูกระงับด้วยหรือไม่
2. **Q-A06-2 ล้างป้ายด้วยประกาศที่ใหม่กว่า** — ตอนนี้ป้ายหายเมื่อประกาศถึงผู้ขอ “ลำดับเดียวกันหรือใหม่กว่า” ส่งถึง (เช่น “รับเรื่อง” ส่งไม่ถึง แต่ “เสร็จ” ส่งถึง) หรือผู้ขอเปิดดูในเว็บ — ยืนยัน
3. **Q-A06-3 ผู้ทำ action ถือว่าเห็นแล้ว** — คำสั่งต้องใช้ revision ล่าสุดจึงตั้ง `last_seen` ของผู้ทำเป็นลำดับใหม่ (ผู้ขอกดยืนยันจากข้อความโดยไม่เปิดหน้า จุดก็หาย) — ยืนยัน
4. **Q-A06-4 ประกาศไหน “จำเป็น”** — A1.2: ป้ายขึ้นเมื่อ “การแจ้งที่จำเป็นยังส่งไม่สำเร็จ” ตอนนี้นับทุกประกาศถึงผู้ขอ (สร้างแทน/รับเรื่อง/เสร็จ/ยกเลิก/เปิดกลับ) — ควรนับเฉพาะบางเหตุการณ์ (เช่น เสร็จรอยืนยัน) หรือไม่
5. **Q-A06-5 ล้าง `NO_ACCOUNT`** — A1.2 “การแจ้งด้วยตนเองใช้ประวัติการติดต่อจริง” → ต้องมีคำสั่ง GM “บันทึกว่าติดต่อแล้ว” (ไม่มีใน spec ว่าอยู่ task ไหน) — เสนอ A17 พร้อมตารางผลการส่ง ([FU-29](../FOLLOW-UPS.md))
