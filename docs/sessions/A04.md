## ส่วนที่ 2 — A04

ทุกคำสั่งผ่าน `POST /api/commands` (มี `command_id`), 1 transaction ต่อคำสั่ง, อ่านทั้งหมดก่อนเขียน; คำสั่งของ GM ต้องมี `expected_revision` (เก่า → 409 `REVISION_CONFLICT` พร้อมสถานะล่าสุด); คนที่อ่านงานไม่ได้ → 404 เหมือนงานที่ไม่มี

### ข้อมูลที่เก็บ

- `requests/{id}`: field ช่วงรอปัจจุบันเดิม (§6.4.1) + ใหม่ `waiting_interval_seq` (จำนวนช่วงที่เคยเปิด) และ `last_reminder_business_date` (โควตาเตือน)
- `requests/{id}/waiting_intervals/w{n}`: `interval_id`, `waiting_on`, `recipient_ids` (คนเดียวที่ตอบได้, A2.1), `started_at`/`started_by_id`, `responded_at`/`responded_by_id`, `exited_at`/`exit_reason` — อ่านผ่าน **`GET /api/requests/:id/waiting-intervals`** ตามสิทธิ์รายละเอียด (เพิ่มใน API matrix)
- history ทุกคำสั่ง (`waiting_started`, `followed_up`, `waiting_party_responded`, `waiting_ended`, `cancelled` + ช่วงรอ, `related_persons_added`, `related_person_removed`, `confidential_flag_set`, `confidential_flag_removed`) อ่านผ่าน `GET /api/requests/:id/history` สิทธิ์เดิม
- โครงสร้าง: ย้าย pipeline การเขียนของ A03 เป็น `apps/api/src/commands/request-change.ts` ใช้ร่วมกันโดย lifecycle, คำสั่ง A04 (`waiting.ts`) และ auto-close ของ worker; `waiting-state.ts` แปลง field ที่เก็บ ↔ state ของ domain; transaction port เพิ่ม `delete`

### การแจ้ง (outbox — ยังไม่ส่งจริง, A07/A08)

- ฝ่ายที่ถูกรอ: `waiting_requested` (event = งาน + ช่วง) ถึง person / ผู้ติดต่อทีมที่เลือก; ทีมไม่มีผู้ติดต่อและภายนอก 3 แบบไม่แจ้ง (`notify: true` → 422 `NOTIFY_NOT_AVAILABLE`); ปิดการแจ้ง person ได้; `waiting_reminder` (event = งาน + วันทำการ, Part 6 §6.6) ผูกกับช่วงเช่นกัน
- GM ที่ถูกรอ (D-S06-4): ได้แจ้ง ไม่ถูกเพิ่มเป็น related ไม่ต้องยืนยันงานลับ และตอบได้
- ตอบกลับ → `waiting_party_responded` ถึง GM ผู้รับผิดชอบ (ไม่มอบหมาย → ทีม GM ตามกติกา A01); ไม่แจ้งคนที่ตอบเอง
- เข้ารอ / กลับมาทำต่อเปลี่ยน status → ผู้ขอและ watcher ได้ `request_waiting` / `request_resumed` (นับเป็นประกาศสถานะ D-A03-7/D-A06-6); เปลี่ยนฝ่ายไม่เปลี่ยน status จึงไม่มีประกาศสถานะ; คนที่ได้ DM ฝ่ายที่ถูกรอแล้วไม่ได้ประกาศสถานะซ้ำ (Q-A04-1)
- worker (F05 §9.3) ก่อนส่งข้อความถึงฝ่ายที่ถูกรอ: ช่วงไม่ใช่ช่วงปัจจุบันแล้ว → `suppressed` `WAITING_ENDED`; ฝ่ายตอบแล้ว → `ALREADY_RESPONDED`; ผู้รับไม่มีสิทธิ์อ่านงานแล้ว (ถูกถอด) → `NO_ACCESS`
- ไม่แจ้งผู้ทำ action เสมอ (D-S08-2)

### สรุปสาธารณะ

- `waiting_on_summary` ตาม D-S09-1: person → ชื่อทีมของคนนั้น (`people/{id}.team_label` ผ่าน `teamLabels` ของ people directory — ตัวนำเข้า CSV ยังเป็น FU-10) ไม่รู้ทีม → “พนักงาน”; ทีม → ชื่อทีม; ผู้รับเหมา → “ผู้รับเหมา”; หน่วยงานรัฐ → ชื่อ; อื่นๆ → “อื่นๆ”; ไม่มีชื่อคน
- ป้าย “ฝ่ายที่รอตอบกลับแล้ว” (`waiting_party_responded`, D-S09-7) ไม่มีผู้ตอบ เวลา หรือหมายเหตุ
- GM summary: `waiting_on_label` = ชื่อคน/ทีม/ชื่อภายนอก

### Preview ก่อนยืนยัน (F05 §9.2, Part 6 §6.6)

`POST /api/requests/:id/waiting-preview` `{ waiting_on, notify? }` และ `POST /api/requests/:id/related-preview` `{ person_ids }` — GM เท่านั้น อ่านอย่างเดียว: ผู้รับแจ้งพร้อมชื่อ, คนที่จะเป็น related, คนที่ต้องได้ grant งานลับ (รวม related เดิมที่ยังไม่มี grant), ต้องยืนยันแยกหรือไม่; คำสั่งตัดสินซ้ำใน transaction

## คำถามค้าง (ไม่เดา — ทำตามข้อที่ระบุไว้ก่อน รอยืนยัน)

1. **Q-A04-1 ผู้ขอที่เป็นฝ่ายที่ถูกรอ** — ตอนนี้ได้ข้อความเดียว (DM “รอคุณ” แบบ `audience: requester`) ไม่ได้ประกาศสถานะ “รอผู้อื่น” ซ้ำ (หลัก 1 รายการต่อผู้รับต่อเหตุการณ์ D-A01-3/D-A02-4) — ยืนยัน
2. **Q-A04-2 ประกาศสถานะเมื่อเข้ารอ/กลับมาทำต่อ** — ผู้ขอและ watcher ได้ `request_waiting` / `request_resumed` (PRD “requester ได้แจ้งเมื่อสถานะเปลี่ยน”, Part 6 §6.10 outbox “แจ้งงานใหม่/สถานะเปลี่ยน/ฝ่ายที่รอ/ผลตอบกลับ”) และนับเป็นประกาศสถานะที่ถูกแทนที่ได้ (D-A03-7) — ยืนยันว่าต้องการแจ้งทั้งสองครั้ง หรือแจ้งเฉพาะเข้ารอ
3. **Q-A04-3 เพิ่มผู้เกี่ยวข้องไม่ส่ง DM** — สอดคล้อง D-A03-1 และ F05 “ผู้เกี่ยวข้องที่เพิ่มไว้เพื่ออ่านงานจึงไม่ถูกส่งเตือนทุกครั้ง” (เห็นจุดอัปเดตใน “คำขอของฉัน”); ตีความ FU-12 “ส่งแจ้งเตือนเฉพาะคนที่มีสิทธิ์” ว่าการแจ้งภายหลังถึงเฉพาะคนที่ยังมีสิทธิ์ (worker `NO_ACCESS`) — ยืนยัน
4. **Q-A04-4 ที่เก็บ `public_visibility_epoch`** — `system_counters/public_visibility` (server เท่านั้น) +1 ทั้งตอนติดธงและปลดธง; aggregate ของ B ใช้เทียบ — ยืนยันที่เก็บ/ชื่อ
5. **Q-A04-5 ชื่อ field ทีม** — `people/{person_id}.team_label` (ตัวนำเข้า FU-10 ต้องเขียน field นี้) — ยืนยัน
