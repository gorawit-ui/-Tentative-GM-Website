## ส่วนที่ 2 — A08

### อีเมล (`apps/worker/src/email.ts`)

- ใช้ `composeNotice` ชุดเดียวกับ Slack: **หัวเรื่อง** `[GM-0427] ข้อความสั้น`; **เนื้อหา** plain text: `GM-0427 ข้อความสั้น` / ชื่อบนบอร์ด / บรรทัดที่ชนิดนั้นเพิ่ม / ว่าง / `เปิดงาน: <ลิงก์>` / ว่าง / `-- ` / “อีเมลนี้ส่งอัตโนมัติ การตอบกลับจะไม่ถูกบันทึกในงาน กรุณาเปิดลิงก์เพื่อตอบ”
- **text/plain อย่างเดียว** ไม่มี HTML จึงไม่มีรูป ไม่มี tracking pixel; ลิงก์เดียวคือหน้างาน; ไม่มีคำอธิบายที่ผู้แจ้งพิมพ์ รูป signed URL หรือหมายเหตุ GM (renderer ไม่รับ field เหล่านี้)
- **UTF-8**: หัวเรื่องและชื่อผู้ส่งเป็น RFC 2047 encoded word (`=?UTF-8?B?…?=` ≤ 75 ตัวอักษร ตัดระหว่างตัวอักษรเท่านั้น พับบรรทัดละคำ) เนื้อหา base64 แบบ CRLF บรรทัดละ 76 — ทุกบรรทัด header เป็น ASCII ≤ 78; test ถอดรหัสด้วยตัวถอดที่เขียนแยกแล้วได้ข้อความเดิมตรงทุกตัว
- กัน header injection: ผู้รับ/ผู้ส่งต้องเป็นที่อยู่เดียวแบบเรียบ (ไม่มีช่องว่าง `,` หรือขึ้นบรรทัด) ไม่งั้น `RangeError`; หัวเรื่องเข้ารหัสทั้งหมด จึงไม่มีทางเพิ่ม header
- `Auto-Submitted: auto-generated` (RFC 3834) กันข้อความตอบกลับอัตโนมัติ

### Gmail adapter (`apps/worker/src/gmail.ts`)

- `POST {GMAIL_API}/gmail/v1/users/me/messages/send` ครั้งเดียวต่อ attempt ด้วย OAuth access token ของกล่องกลาง (`gmail.send` เท่านั้น ไม่อ่านกล่อง) ส่งในนาม `GM_MAIL_FROM` / `GM_MAIL_FROM_NAME` (ค่าเริ่มต้น “ทีม GM”; ต้องเป็นกล่อง @tdfb.co หนึ่งกล่อง); ไม่ retry เอง

| คำตอบ | ผล adapter | สถานะรายการ |
|---|---|---|
| 200 | accepted `gmail:{message id}` | `provider_accepted` |
| ผู้รับไม่ใช่อีเมลบริษัท (ตรวจก่อนส่ง) / 400 `Invalid To header` | permanent `GMAIL_INVALID_RECIPIENT` | `failed` + ป้ายผู้ขอยังไม่ได้รับแจ้ง |
| เพดานของแอปเต็ม (30/นาที, 500/วัน) | deferred `EMAIL_CAP_REACHED` | `pending` ถึงนาทีถัดไป / 00:00 กรุงเทพ **ไม่นับ attempt** (ไม่ทิ้งข้อความ, §6.10) |
| 429 (+ Retry-After) / 403 `dailyLimitExceeded`, `userRateLimitExceeded`, `rateLimitExceeded`, `quotaExceeded` | retryable `GMAIL_RATE_LIMITED` / `GMAIL_QUOTA_EXCEEDED` | `pending` ตาม max(back-off A02, Retry-After) |
| ขอ token ไม่ได้ / ต่อไม่ติด / 503 | retryable `GMAIL_AUTH_UNAVAILABLE` / `GMAIL_UNREACHABLE` / `GMAIL_HTTP_503` | `pending` |
| ส่งแล้วไม่ตอบใน timeout (10 วินาที) / 5xx อื่น / คำตอบอ่านไม่ได้ | unknown | `delivery_unknown` ไม่ส่งซ้ำเอง |
| 401 / 403 อื่น / 4xx อื่น | permanent `GMAIL_UNAUTHORIZED` / `GMAIL_FORBIDDEN` / `GMAIL_HTTP_…` | `failed` |

- เพดานของแอป (`email-quota.ts`): `system_counters/email_send` (server เท่านั้น; แถวใน ACL fixture) เก็บจำนวนของนาทีนี้และวันนี้ (วันกรุงเทพ) อัปเดตใน transaction ก่อนส่งทุกฉบับ; `@gm/time` ใหม่ `startOfNextBangkokDay`
- `provider-http.ts`: Retry-After และความล้มเหลวของเครือข่าย (ก่อน/หลังส่ง) ใช้ร่วม Slack และ Gmail
- โหมด runtime ยัง `local` / `disabled` เท่านั้น — ต่อ Gmail จริง (OAuth refresh token ใน Secret Manager, send-as, โหมด `gmail`) หลัง P7-ADMIN-02 → [FU-34](../FOLLOW-UPS.md)

## คำถามค้าง (ไม่เดา — ทำตามข้อที่ระบุไว้ก่อน รอยืนยัน)

1. **Q-A08-1 หมายเหตุตอนเข้ารอ** — D-A07-1 พูดถึง “หมายเหตุที่ GM ใส่ตอนเข้ารอ” แต่ API และ sheet “รอผู้อื่น” ใน UI-07 ยังไม่มีช่องนี้ จึงเพิ่ม `note` (ไม่บังคับ) ใน `enter_waiting` / `change_waiting_party` เก็บใน interval และ history `waiting_started` (ผู้ขอและผู้เกี่ยวข้องที่อ่านรายละเอียดได้เห็นใน history) — ยืนยันว่าเห็นใน history ได้ หรือให้เห็นเฉพาะ GM และฝ่ายที่ถูกรอ; ช่องในฟอร์ม → [FU-35](../FOLLOW-UPS.md)
2. **Q-A08-2 “GM ที่รอ” ในการเตือนซ้ำ** — ใช้ GM ที่กด “ส่งเตือนอีกครั้ง” (คนทำ action) ไม่ใช่ GM ที่เริ่มรอ — ยืนยัน
3. **Q-A08-3 “ฝ่ายไหนตอบ”** — แสดงชื่อคนที่ตอบ + ทีมในวงเล็บ เช่น “สมชาย (ทีมบัญชี) ตอบกลับแล้ว” (ไม่มีทีม → ชื่ออย่างเดียว) — ยืนยัน หรือให้ใช้ป้ายฝ่ายที่รอ
4. **Q-A08-4 งานลับตอนงานเสร็จ** — คงบรรทัดเวลาปิดอัตโนมัติและ “ถ้ายังไม่เรียบร้อย …” (ไม่มีชื่องาน) ตามเหตุผล D-A07-1 ว่างานอาจปิดเองโดยผู้ขอไม่ได้ตรวจ — ยืนยันว่าวันปิดอัตโนมัติแสดงในงานลับได้
5. **Q-A08-5 เครื่องหมายคำพูด** — ใช้ `'ฝั่งฉันเรียบร้อยแล้ว'` / `'ยังไม่เรียบร้อย'` ตามที่พิมพ์ใน D-A07-1 (หน้าจอใน spec ใช้ “ ”) — ยืนยัน
6. **Q-A08-6 Slack `account_inactive`** — ใน Slack หมายถึงบัญชีของแอป/token ไม่ใช้งาน (ไม่ใช่ผู้รับ) จึงยังเป็น `failed SLACK_ACCOUNT_INACTIVE` ไม่ส่ง email แทน; รายงาน A07 จัดรวมกับ “ผู้ใช้ถูกปิด” ผิดไป — ยืนยัน
7. **Q-A08-7 sandbox ใน `local`** — ใช้กติกาเดียวกับ dev: ไม่ตั้ง `GM_NOTIFY_SANDBOX` = ไม่ส่งใคร (รายการเป็น `suppressed`) แม้โหมด local จะไม่ส่งออกนอกเครื่องอยู่แล้ว — ยืนยัน
8. **Q-A08-8 sandbox กับป้ายผู้ขอ** — รายการที่ `suppressed NOT_IN_SANDBOX` ไม่ขึ้นป้าย “ผู้ขอยังไม่ได้รับแจ้ง” (เหมือน suppressed อื่น) — ยืนยันสำหรับ dev
9. **Q-A08-9 อีเมลตีกลับ** — Gmail API ปฏิเสธเฉพาะที่อยู่ที่รูปแบบผิด; ที่อยู่รูปแบบถูกแต่ไม่มีจริงจะ `provider_accepted` แล้วตีกลับเข้ากล่องกลาง ซึ่งระบบอ่านไม่ได้ (`gmail.send` อย่างเดียว ตาม Part 6) — ยอมรับเป็นข้อจำกัดหรือไม่ (รายชื่อมาจาก CSV ของ Admin จึงควรเกิดน้อย)
10. **Q-A08-10 ชื่อผู้ส่ง** — ค่าเริ่มต้น “ทีม GM” (`GM_MAIL_FROM_NAME`) และที่อยู่ผู้ส่งรอ P7-ADMIN-02 — ยืนยันชื่อที่แสดง
11. **Q-A08-11 เพดาน** — 30 ฉบับ/นาที 500 ฉบับ/วันตาม assumption ของ Part 6 §6.10 — ยืนยันกับเพดานจริงของกล่องกลางตอน P7-ADMIN-02
12. **Q-A08-12 Reply-To** — ไม่ตั้ง Reply-To (ตอบแล้วเข้ากล่องกลางซึ่งไม่ถูกบันทึก ท้ายอีเมลบอกไว้แล้ว) — ต้องการให้ตอบกลับไปที่อื่น เช่น กลุ่มทีม GM หรือไม่

## Risk ที่ยังค้าง

- รูปแบบ error ของ Gmail (`Invalid To header`, reason ของโควตา) อิงเอกสาร Gmail API ไม่ได้ทดสอบกับ Gmail จริง (ห้ามต่อใน task นี้) — ต้องยืนยันใน sandbox (FU-34); รหัสที่ไม่รู้จักเป็น `failed GMAIL_…` ให้เห็น
- การขอ access token จาก refresh token (OAuth) ยังไม่ได้ทำ (`accessToken` เป็น dependency) — FU-34
- เพดานใช้ document เดียว (`system_counters/email_send`) เขียนทุกฉบับ — ≤ 30 ครั้ง/นาที ต่ำกว่าเพดานการเขียนต่อ document มาก
- local dev ที่ไม่ตั้ง `GM_NOTIFY_SANDBOX` จะเห็นรายการเป็น `suppressed` ทั้งหมด (ตั้งใจ, Q-A08-7)
- โหมด runtime ยังไม่ใช้ Slack/Gmail จริง — ก่อน pilot ต้องทำ FU-33 + FU-34 ไม่งั้นแจ้งได้แค่ในแอป (P7-PILOT-01 ยอมรับได้แต่ต้องรู้ช่องทางที่ขาด)
