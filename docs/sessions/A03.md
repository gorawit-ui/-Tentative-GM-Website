## ส่วนที่ 2 — A03

### คำสั่ง (`POST /api/commands`)

| `type` | payload (ทุกตัวมี `request_id` + `expected_revision`) | ใคร | domain (S05) |
|---|---|---|---|
| `accept_request` | `take_over?` (D-S05-5) | GM | `acceptRequest` |
| `complete_request` | `resolution_summary` | GM | `completeRequest` (ปฏิทินบริษัทเป็น confirmation snapshot) |
| `confirm_completion` | `completion_cycle_id` | ผู้ขอ | `confirmCompletion` |

ผลลัพธ์: `{ request_id, request_number, revision, status }` (ส่งซ้ำ `command_id` เดิม → ผลเดิม `replayed: true`)

### transaction เดียวต่อคำสั่ง (`apps/api/src/commands/lifecycle.ts`)

อ่านทั้งหมดก่อนเขียน:
1. `requests/{id}` + `gm_request_details/{id}` → อ่านไม่ได้ตาม ACL หรือไม่มีงาน → **404 `REQUEST_NOT_FOUND`** (ไม่บอกว่ามีงานอยู่)
2. คนที่ทำได้: GM (`GM_ONLY` 403) / ผู้ขอตัวจริง (`REQUESTER_ONLY` 403)
3. **`expected_revision` ≠ `revision`** → **409 `REVISION_CONFLICT`** + `current: { revision, status, closed? }`; ถ้าเป็นการรับเรื่องที่ GM อื่นรับไปแล้ว → **409 `ALREADY_ACCEPTED`** + `current.assignee_display` (ชื่อผู้รับ) ไม่เขียนอะไรเลย
4. domain rule (รหัสเดิมของ S05 เช่น `REASON_REQUIRED`, `STALE_COMPLETION_CYCLE` → 422)
5. routing facts (ปฏิทินบริษัท, หมุดของ GM), ชื่อ, ตัวนับงานภายใน, `user_state` ของผู้เกี่ยวข้อง

แล้วเขียน:
- `requests/{id}`: field lifecycle + `revision` +1 + `activity_seq` +1 + `last_activity_at`; เสร็จแบบรอยืนยันเก็บ `confirmation_calendar_snapshot` (hash/source, Part 6 §6.7); งานที่ไม่อยู่ `waiting` ไม่เหลือ field ของช่วงรอปัจจุบัน
- `request_summaries/{id}` (งานไม่ลับ) + `gm_request_summaries/{id}` สร้างใหม่จาก record เดียวกัน
- `requests/{id}/history/r{revision}`: `accepted` (`previous_assignee_id`) / `completed` (`resolution_summary`, `completion_cycle_id`, `auto_close_due_at`) / `closed` (`closure_kind`) / `not_resolved` / `cancelled` / `reopened` (`reason`) พร้อมผู้ทำ เวลา revision
- `board_counters/public` (D-S09-4): งานลับนับเมื่อยังไม่ปิด/ไม่ยกเลิก — เสร็จแบบไม่มีผู้ขอ/ยืนยัน/auto-close/ยกเลิก −1, เปิดกลับ +1, รอยืนยันยังนับ
- `user_state/{คน}/requests/{id}`: `activity_seq`, `last_activity_at` ของผู้ขอ, related ที่มีสิทธิ์ และ watcher (เฉพาะงานไม่ลับ) — ไม่รวมผู้ทำ action; ไม่สร้างเอกสารใหม่ (Q-A03-5)
- `gm_profiles/{gm}`: ปลด `focus_request_id` เมื่องานออกจาก `in_progress` (D-S07-6) field อื่นคงเดิม; หมุดงานอื่นไม่แตะ
- `scheduled_work/auto_close-{id}-c{cycle}` เมื่อเสร็จแบบรอยืนยัน (`next_run_at` = `auto_close_due_at`, key = request + completion cycle ตาม §6.9)
- `outbox`: แจ้งเมื่อสถานะเปลี่ยน — **ผู้ขอ** (`audience: requester`, PRD §6.9 / US-08; งานเสร็จรอยืนยันมี `auto_close_due_at`) และ **watcher** ของงานไม่ลับ (`audience: watcher`, U1) **ไม่แจ้งผู้ทำ action** (D-S08-2); event = `{id}:r{revision}` จึงส่งซ้ำ `command_id` ไม่เกิดรายการใหม่; การปิด (ยืนยัน/auto-close) ไม่เปลี่ยนสถานะจึงไม่แจ้ง (Q-A03-3)

### Auto-close (job ของ tick เดียวจาก A02)

`autoCloseInTransaction` ใช้ pipeline เดียวกันในชื่อ `system`: ตรวจสถานะล่าสุด (`completed`, ยังไม่ปิด, รอบเดียวกัน, ถึงเวลา) แล้วปิด `auto_closed` โดยไม่แตะ `last_updated_at`; worker `jobs/auto-close.ts` เรียกผ่าน `runChecked` — ผู้ขอตอบก่อน/เปิดกลับ/รอบใหม่ → job `superseded`, ยังไม่ถึงเวลา → reschedule; ลงทะเบียนใน `apps/worker/src/main.ts`

ผู้ขอกับ tick ชนกัน: ทั้งคู่เขียน `requests/{id}` ใน transaction → Firestore ให้ฝ่ายหนึ่ง retry แล้วเห็นสถานะใหม่: ผู้ขอได้ 409 (`REVISION_CONFLICT`, `closed: true`) หรือ job เป็น `superseded` — ปิดครั้งเดียว history `closed` รายการเดียว

### แก้ของ A02 ที่พบระหว่างทำ

- **ปล่อย tick lease = ลบ `lease_until`** (เดิมตั้งเป็นเวลาจบ): test ของ A03 ที่ย้อนเวลาเจอ tick ถัดไปเป็น `busy` ทั้งที่ tick ก่อนจบแล้ว — ในระบบจริงเกิดได้เมื่อนาฬิกาสองเครื่องต่างกันเล็กน้อย; ปรับ expectation ใน `worker-tick.test.ts` ให้ตรง
- worker รองรับ `audience: watcher` และระงับ (`suppressed`, `NO_ACCESS`) เมื่องานกลายเป็นงานลับก่อนส่ง

## คำถามค้าง (ไม่เดา — ทำเฉพาะที่ spec บอกชัด)

1. **Q-A03-1 related persons** — spec ระบุแจ้งผู้ขอ (PRD §6.9) และ watcher (U1) เมื่อสถานะเปลี่ยน แต่ไม่ระบุ related persons → ตอนนี้ **ไม่แจ้ง** related (เห็นจุดอัปเดตผ่าน `user_state`) — ให้แจ้งด้วยหรือไม่
2. **Q-A03-2 แจ้ง GM ผู้รับผิดชอบ** — ผู้ขอกด “ยังไม่เรียบร้อย” (งานกลับมา `in_progress`) หรือยืนยันปิด ตอนนี้ **ไม่มี** outbox ถึง assignee (UI-15 ไม่มี template) — ให้แจ้ง assignee เมื่อ “ยังไม่เรียบร้อย” หรือไม่
3. **Q-A03-3 แจ้งเมื่อปิด** — ยืนยันปิด/auto-close ไม่เปลี่ยน `status` จึงไม่แจ้งใคร (รวม watcher) — ให้แจ้งผู้ขอ/watcher เมื่อ auto-close หรือไม่
4. **Q-A03-4 รับต่อจาก GM อื่น** — `accept_request` + `take_over` บันทึก `previous_assignee_id` ใน history แต่ไม่แจ้ง GM คนเดิม — ให้แจ้งหรือไม่
5. **Q-A03-5 unread clock** — ตีความ Part 6 §6.4.1 (`activity_seq`/`last_activity_at`) เป็น: request เก็บ `activity_seq` (+1 ทุกเหตุการณ์ lifecycle) และ `user_state` ของคนที่เห็นเหตุการณ์เก็บ `activity_seq` ล่าสุดที่เขาเห็น (A06 จะเทียบกับ `last_seen_activity_seq` ตอนเปิดดู) ไม่สร้าง `user_state` ใหม่ให้ watcher (FU-08) — ยืนยันสำหรับ A06
6. **Q-A03-6 `confirmation_calendar_snapshot` ใน `requests/{id}`** — Part 6 §6.4.1 ให้เป็น field ของงาน จึงเก็บใน `requests/{id}` ซึ่งผู้ขอ/related อ่านได้ (มีเพียงวันทำการ/วันหยุดบริษัท + hash) ต่างจาก D-S09-3 ที่ไม่ให้เว็บอ่าน `calendars` ตรง — ใช้ได้ หรือควรย้ายไปเอกสาร GM-only
7. **Q-A03-7 ประกาศสถานะที่ล้าสมัย** — ประกาศที่ยังไม่ส่งแล้วงานเปลี่ยนต่อ (เช่น “รับเรื่องแล้ว” ค้าง แล้วถูกยกเลิก) ตอนนี้ยังส่งตามลำดับ (§6.9 ให้ recovery “ไม่ส่งเหตุการณ์ revoke/cancel/supersede”) — ให้ worker ระงับประกาศที่ revision ของงานผ่านไปแล้วหรือไม่

## Risk ที่ยังค้าง / ส่วนที่เหลือ

- ยกเลิกงานที่อยู่ `waiting` ผ่าน API: ล้าง field ช่วงรอปัจจุบันใน request แล้ว แต่ยังไม่ปิดเอกสาร `waiting_intervals/{n}` (ยังไม่มี waiting persistence) → [FU-26](../FOLLOW-UPS.md) A04; ตอนนี้ยังสร้างสถานะ `waiting` ผ่าน API ไม่ได้
- `work_calendar_snapshot` ตอนสร้างงาน (Part 6 §6.4.1 “งาน A เก็บ work calendar บริษัทตั้งแต่สร้าง”) A01 ยังไม่เขียน → [FU-27](../FOLLOW-UPS.md)
- `gm_profile_summaries` (focus แบบปลอดภัย) ยังไม่มีใครเขียน การปลดหมุดแก้เฉพาะ `gm_profiles` → [FU-28](../FOLLOW-UPS.md) A23
- คำสั่ง `watch_request` ยังไม่อัปเดต `watcher_count` ใน summary และไม่สร้าง `user_state` ของ watcher (คำสั่ง lifecycle ถัดไปจะ rebuild ให้ถูก) → รวมใน [FU-08](../FOLLOW-UPS.md)
- auto-close job + handler ทำใน A03 (เป็นส่วนของ lifecycle persistence ตาม acceptance “confirm/auto-close compete”); ส่วนที่เหลือของ A05 คือ stale และ presence reset
- ประกาศสถานะยังส่งผ่าน adapter local เท่านั้น ข้อความจริง/template งานลับอยู่ A07/A08
